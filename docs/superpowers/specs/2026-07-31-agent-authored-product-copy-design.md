# Вординг Easy UI для прототипов, собранных агентом

Дата: 2026-07-31
Статус: концепция одобрена в диалоге

## 1. Цель

Первый слой интерфейса должен объяснять ценность Easy UI продакту:

- продакт описывает идею внешнему агенту;
- Codex или Claude со скиллом Easy UI собирает прототип;
- агент использует компоненты той же дизайн-системы, что и продукт;
- пользователь получает прототип, который выглядит и ощущается как продукт, а
  затем проверяет его, делится им и вносит точечные правки.

Easy UI не позиционируется как ручной конструктор или встроенный AI-чат. Агент
работает во внешнем чате и пишет прототипы, компоненты и композиции через
существующие инструменты авторинга. Приложение показывает результат и даёт
поверхности проверки, публикации, обмена и ограниченных правок.

## 2. Продуктовая модель и язык

Роли формулируются однозначно:

- **агент создаёт** прототипы, компоненты и композиции;
- **пользователь направляет** агента, смотрит результат, проверяет его, делится
  им и правит контент, ассеты и доступные параметры;
- **Easy UI хранит и показывает** собранные артефакты и их версии.

Основной артефакт в пользовательском тексте — **прототип**. Слово
**сценарий** используется только для пути внутри прототипа, например в разделе
«Сценарии». В первом продуктовом слое не используются слова «живой»,
«кликабельный» и «флоу»: они описывают механику или внутреннюю модель, а не
пользовательский результат.

Агент называется просто «агентом», без повторяющегося AI-маркетинга. Codex и
Claude упоминаются только в инструкции запуска, где это помогает выполнить
следующий шаг.

## 3. Галерея

### 3.1. Хиро

Заголовок сохраняет динамический счётчик и согласуется по числу:

- `1 прототип, который ощущается как продукт`;
- `2 прототипа, которые ощущаются как продукт`;
- `5 прототипов, которые ощущаются как продукт`;
- без загруженного счётчика: `Прототипы, которые ощущаются как продукт`.

Подзаголовок тоже согласуется с числом:

- для единственного показанного прототипа:
  `Агент быстро собирает его из компонентов вашей дизайн-системы.`;
- во всех остальных состояниях:
  `Агент быстро собирает их из компонентов вашей дизайн-системы.`

Счётчик остаётся фактическим числом прототипов в текущей выдаче. В заголовке
нет слов «сценарии», «флоу» или «кликабельные».

### 3.2. Главное действие

Ручное действие «Новый прототип» заменяется на:

> Собрать с агентом

Кнопка не имитирует встроенный чат. Она открывает короткий информационный
диалог:

- заголовок: `Соберите прототип с агентом`;
- текст:
  `Откройте Codex или Claude со скиллом Easy UI и опишите идею. Агент соберёт прототип и добавит его в галерею.`;
- действие закрытия: `Понятно`.

Импорт бандла остаётся отдельным вторичным действием: это перенос готовых
артефактов, а не ручной авторинг.

### 3.3. Пустые состояния

Когда прототипов нет:

- заголовок: `Попросите агента собрать первый прототип`;
- описание: `Опишите идею — готовый прототип появится здесь.`;
- главное действие: `Собрать с агентом`;
- вторичное действие: `Импортировать бандл`.

Когда в дизайн-системе нет доступных компонентов:

- заголовок: `В дизайн-системе пока нет компонентов`;
- описание:
  `Агент добавит нужные компоненты перед сборкой прототипа.`;
- главное действие: `Собрать с агентом`.

Состояния пустого поиска и фильтров остаются функциональными и не повторяют
продуктовое обещание.

## 4. Библиотека

### 4.1. Хиро

Заголовок:

> Компоненты вашей дизайн-системы

Подзаголовок при непустой библиотеке:

> Агент использует их в прототипах и добавляет новые, когда нужно.

Подзаголовок при пустой библиотеке:

> Агент добавит нужные компоненты при сборке прототипа.

Счётчики компонентов и дизайн-систем не входят в хиро: они не объясняют
ценность и утяжеляют первую фразу. Их можно оставить в фильтрах и секциях
каталога.

Постоянная кнопка «Опубликовать компонент» удаляется. Публикация — обязанность
агента, а библиотека для продакта является витриной доступных строительных
блоков.

### 4.2. Пустые состояния

Когда компонентов нет:

- заголовок: `Компонентов пока нет`;
- описание:
  `Агент добавит и опубликует нужные компоненты при сборке прототипа.`;
- главное действие: `Собрать с агентом`, открывающее ту же инструкцию, что и в
  галерее.

Когда композиций нет:

- заголовок: `Композиций пока нет`;
- описание:
  `Агент создаёт их из повторяющихся частей прототипов.`

Ручные инструкции с HTTP API и TSX удаляются из продуктовых пустых состояний.
API и техническая документация остаются доступны в специальном разделе для
агентов и разработчиков.

### 4.3. Поиск и превью

Короткие тексты поиска:

- пример в поле поиска:
  `Например, кнопка оплаты или экран успеха`;
- пустой результат:
  `Ничего не нашли. Попробуйте описать задачу иначе.`

«Живое превью» в пользовательском тексте сокращается до «превью»:

- `Живое превью компонента …` → `Превью компонента …`;
- `Живого превью нет: у компонента не заданы example-props` →
  `Превью недоступно: не заданы примерные параметры.`

Технические имена `example-props`, HTTP API и TSX не выводятся в первом
продуктовом слое.

## 5. Правки вместо ручного редактора

Одновременно с удалением ручного авторинга пользовательское название
«Редактор» меняется на «Правки»:

- сегмент прототипа: `Правки`;
- пункт меню карточки: `Правки`;
- document title: `<название> · Правки`;
- недоступное состояние: `Правки недоступны`.

Переименование нельзя выпускать раньше функционального ограничения ручного
редактора: до этого слово «Правки» обещало бы более узкую поверхность, чем
фактически доступна.

Точный набор разрешённых изменений определяется отдельной задачей удаления
ручного флоу. Этот документ фиксирует только роль поверхности: правки
существующего результата, а не сборка прототипа с нуля.

## 6. Сквозные замены

В видимых продуктовых строках:

- вид `Продуктовый флоу` называется `Продуктовый прототип`; внутренний id
  `product-flow` не меняется;
- сообщения о состоянии флоу формулируются через прототип и экран;
- «живые контролы» называются «настройками»;
- «живое превью» называется «превью».

Технические комментарии, идентификаторы API, поля формата `flows` и тестовые
фикстуры не переименовываются. Раздел «Сценарии» сохраняется: он действительно
показывает пути внутри прототипа.

## 7. Границы задачи

Входит в последующую реализацию:

- новые хиро-тексты галереи и библиотеки;
- согласование единственного числа в динамическом хиро;
- агентский информационный диалог и переиспользование его CTA в пустых
  состояниях;
- удаление ручных CTA создания из первого слоя;
- новые пустые состояния и прямые замены запрещённого вординга;
- переименование «Редактор» в «Правки» в одной поставке с ограничением ручного
  авторинга.

Не входит:

- встроенный чат или запуск Codex/Claude из браузера;
- изменение API авторинга;
- установка или обновление скиллов Codex/Claude;
- автоматическое обновление галереи в реальном времени;
- изменение модели прототипов, компонентов, композиций или сценариев;
- полный редакторский аудит технических и административных экранов.

## 8. Проверка

Реализация должна подтвердить:

1. Заголовок галереи грамматически корректен для `1`, `2`, `5`, `11` и `21`.
2. Хиро и пустые состояния не обещают встроенный AI-чат.
3. В первом слое нет ручных CTA создания прототипов, компонентов или
   композиций.
4. «Собрать с агентом» в галерее, библиотеке и пустых состояниях открывает одну
   и ту же инструкцию.
5. В пользовательских строках первого слоя отсутствуют «живой»,
   «кликабельный» и «флоу», кроме технически исключённых идентификаторов и
   комментариев.
6. «Сценарии» остаются названием пути внутри прототипа.
7. Импорт, просмотр, проверка, публикация, обмен и допустимые правки остаются
   достижимыми.
8. Unit- и E2E-тесты проверяют новые заголовки, отсутствие старых CTA и
   агентский диалог.
