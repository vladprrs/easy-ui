# Политика авторинга для агентов: **переиспользуй, прежде чем создавать**

Канон. Единственный источник правил для любого агента (Claude Code, Codex, внешний клиент),
который создаёт или правит компоненты, композиции и прототипы easy-ui.
Скиллы (`.claude/skills/*/SKILL.md`), `AGENTS.md` и `CLAUDE.md` ссылаются сюда и не переписывают
эти правила своими словами.

Границы:

- **что именно возвращают эндпоинты** — `docs/server-api.md`
  ([reuse gate](server-api.md#reuse-gate-при-создании-и-публикации-компонента),
  [поиск кандидатов](server-api.md#поиск-кандидатов-на-переиспользование),
  [аудит решений](server-api.md#аудит-решений-гейта));
- **как устроен матчер и почему выбраны пороги** — `docs/plans/2026-07-31-component-reuse-enforcement.md`
  и отчёт `docs/audit/2026-07-31-matcher-calibration.md`;
- **словарь ролей** — `docs/canonical-roles.md`;
- **здесь** — что обязан делать агент, в императивах и точных командах.

Все команды ниже — `driver.mjs` из `.claude/skills/author/` (запускать из этого каталога либо
по пути `node .claude/skills/author/driver.mjs`). Любой verb принимает `--json`.

## 0. Правило

> Новый компонент — последнее средство. Сначала найди существующий, потом расширь существующий,
> и только потом создавай новый.

Это правило **не является рекомендацией**: `POST /api/components` и `POST /api/bundles/import`
проверяют его на сервере в транзакции. Инструкция, которую агент не прочитал, не может создать
дубликат — но агент, который не прочитал инструкцию, потеряет время на терминальный `409`.

## 1. Дешёвый цикл открытия каталога

Три команды вместо одного дампа. Никогда не начинай с полного дампа каталога.

```bash
node driver.mjs catalog list yandex-pay
node driver.mjs catalog search yandex-pay --intent "Let a customer rate a product from one to five stars" --limit 5 --json
node driver.mjs catalog get yandex-pay yp-box YpText --json
```

| Команда | Что даёт | Когда |
|---|---|---|
| `catalog list <ds>` | инвентарь: `kind, id, name, version, atomicLevel, deprecated, events, slots, description` | всегда первым шагом; отсюда берутся имена |
| `catalog search <ds> --intent <text>` | кандидаты матчера с `score`, `blocking`, `reasons` | перед созданием нового компонента и когда не ясно, есть ли готовый |
| `catalog get <ds> <artifact…>` | exact definition (props/JSON Schema, examples, payloads) только названных артефактов | после выбора — по 3–10 компонентам экрана |
| `catalog <ds> [out.json] [--full]` | компактный (или с `--full` — полный) машинный дамп | только когда действительно нужен весь каталог: инвентаризация, миграции, генерация SDK |

Замер на локальной БД (37 активных `yandex-pay`, оценка токенов = символы ÷ 4; см. §7 «как
считалось»): полный дамп `catalog --full` — **107 035 символов ≈ 27k токенов**; `catalog list` —
**9 377 символов ≈ 2.3k токенов**; `catalog get` одного компонента — медиана **1 689 символов
≈ 0.4k токенов**. На прод-каталоге (115 активных публикаций) те же проекции дают
**≈ 83k** против **≈ 7k** токенов. Цикл `list` + `get` по десяти использованным компонентам —
**≈ 9k токенов**, то есть примерно на порядок дешевле дампа при том же материале для авторинга.

`catalog list` намеренно **не** содержит `propsJsonSchema` и примеров: props валидируются строго,
поэтому перед написанием документа обязательно взять exact definition через `catalog get`.

## 2. Прежде чем создавать компонент

1. Сформулируй `intent` — продуктовую задачу одной фразой, 8..500 символов после trim,
   минимум один токен вне стоп-набора `component`, `компонент`, `element`, `элемент`, `ui`.
   «Новый UI-компонент» — не intent; «Let a customer rate a product from one to five stars» — intent.
2. `catalog search <ds> --intent "<intent>" --json`. Прочитай кандидатов.
3. Реши по порядку:
   - **кандидат покрывает задачу** → используй его, ничего не создавай;
   - **кандидат почти покрывает** → расширь его новой ревизией (`driver.mjs component <его-id> …`
     — обновление, `intent` не требуется и гейт создания не запускается), non-breaking:
     новый проп с дефолтом, новый слот, новая ветка рендера;
   - **ни один не подходит** → создавай новый и объясни в `intent`, чем он отличается.
4. Создание:

```bash
node driver.mjs component rating-stars RatingStars examples/rating-stars.tsx \
  --design-system yandex-pay \
  --intent "Let a customer rate a product from one to five stars"
```

`--intent` требуется драйвером только на ветке создания (когда `GET /components/<id>` дал 404);
для обновления он не передаётся и не нужен. На создании драйвер сам делает authoritative
discovery (`POST /api/catalog/candidates` c `proposed`) и печатает кандидатов **до** мутации;
это не заменяет серверную проверку — гейт пересчитывается заново внутри транзакции создания.

Предпочитай **композицию** новому компоненту, когда задача — сборка существующих:

```bash
node driver.mjs composition checkout-summary composition.json --design-system yandex-pay
node driver.mjs composition publish checkout-summary
```

## 3. `409` — терминальная остановка

Три кода — `component_reuse_required`, `canonical_role_conflict`, `catalog_changed` — приходят в
конверте `error` и означают одно и то же для агента: **STOP**.

- `retryable: false`. **Не ретраить**, не менять id/имя ради обхода, не звать `--force-new`
  автоматически. Драйвер печатает кандидатов и завершается с exit code `2`.
- Сохрани `decisionId` — по нему решение находится в аудите (`driver.mjs audit reuse`, только админ)
  и на него ссылаются при эскалации.
- Поле `resolution` считает сервер: `"reuse"` — хотя бы один блокирующий кандидат способен выразить
  требуемое (в его `propsDelta` пусты `removed` и `typeChanged`); `"escalate"` — ни один не способен.
- `candidates[].propsDelta` показывает, каких пропов не хватает кандидату: это план расширения
  существующего компонента.
- `repeatedAttempts` — сколько раз этот же актор уже упирался в ту же блокировку (`null`, если
  аудит недоступен). Ненулевое значение означает «ты ходишь по кругу; иди к человеку».
- `catalog_changed` — каталог сдвинулся между discovery и мутацией. Заново выполни discovery и
  покажи человеку **новое** решение; прежнее подтверждение не переносится.
- `canonical_role_conflict` — роль из `definition.canonicalFor` уже занята другим компонентом
  системы. Либо используй занявший её компонент, либо убери `canonicalFor` из своей ревизии
  (см. `docs/canonical-roles.md`).

**Эскалация.** Обход существует только как двухфазное действие человека и только у администратора:
человек читает кандидатов и `decisionId`, принимает решение, и после этого администратор повторяет
команду с `--force-new --reason "<20..500 символов, человеческое обоснование>"`:

```bash
node driver.mjs component rating-stars RatingStars examples/rating-stars.tsx \
  --design-system yandex-pay \
  --intent "Let a customer rate a product from one to five stars" \
  --force-new --reason "Product owner approved a distinct rating interaction for this flow"
```

Драйвер передаёт server-authored `overrideTemplate` (`catalogRevision` + полный `candidateKeys`)
дословно; подменять этот набор своей выборкой нельзя. Не-администратор получит `403 admin_required`.
Каждый `force_new` — именная запись в append-only аудите.

## 4. Фаза гейта

Инстанс работает в `shadow` либо в `enforce`. Единственный поддерживаемый способ узнать фазу:

```bash
curl -s "$EASYUI_API/capabilities" | jq .reuseGate
# {"mode":"shadow","intentRequired":false,"policyVersion":1}
```

`intentRequired` истинно ровно в `enforce`. **Пиши клиента, который умеет обе фазы**: всегда шли
`intent` (в `shadow` он тоже валидируется и попадает в аудит) и никогда не рассчитывай, что
создание дубликата пройдёт. В `shadow` блокирующее совпадение не отменяет create, но возвращает
`warnings[]` и пишет решение `would_block` — эти предупреждения читать и разбирать, а не глушить.

## 5. Обновления, публикация, импорт

- **Обновление компонента** (`PUT /components/:id` → `driver.mjs component <существующий-id> …`)
  гейт создания не проходит: это не новый артефакт.
- **Публикация** (`POST /components/:id/publish`) не даёт `component_reuse_required`, но проверяет
  уникальность канонической роли и печатает warn-предупреждение о похожих артефактах.
  Сам публикуемый артефакт из корпуса исключён — «дубликат самого себя» невозможен.
- **Импорт бандла** (`POST /bundles/import`) проходит тот же гейт по-элементно: заблокированный
  элемент — `{"action":"error","detail":"reuse_blocked"}` в отчёте. Обход — `mode=dry-run`, затем
  `mode=apply` с админским `reuseOverride` в теле. Детали — `docs/server-api.md`.

## 6. Метаданные, которые делают поиск возможным

Каждый новый компонент обязан объявить в `definition`:

- `description` — что делает и для какой задачи (участвует в поиске);
- `atomicLevel` — и не завышенный;
- `scope` — если применимо;
- `canonicalFor: ["<role-slug>"]` — **только** если компонент действительно канонический выбор
  системы для этой продуктовой роли, и слаг взят из `docs/canonical-roles.md`;
- `replacement` — если ревизия заменяет устаревший артефакт.

Пустая мета — это не «нейтрально»: она делает компонент невидимым для поиска и для гейта, то есть
готовит следующий дубликат.

## 7. Как считались числа §1

Bun-скрипт поверх копии серверной БД: `catalogManifest(db, ds)` из `server/routes/components.ts`,
затем те же три проекции, что делает CLI, — `fullCatalog`, `compactCatalog`, `catalogListLines`.

Измерялись символы сериализованных ответов, оценка токенов — «символы ÷ 4» (для JSON это скорее
оптимистично, чем пессимистично). Локальная БД содержит 37 активных публикаций `yandex-pay`;
прод-значения получены линейной экстраполяцией на 115 активных публикаций (число из отчёта
калибровки T0). Порядок величины совпадает с оценкой ≈8k против ≈50k токенов, зафиксированной в
плане §1.2 A8.
