# План: Component Reuse Enforcement and Agent Discovery (проект 2)

Дата: 2026-07-31 · Версия: **v3** (после двух раундов адверсариального ревью, 3 линзы)
Спека: `docs/superpowers/specs/2026-07-30-component-reuse-enforcement-design.md`
Зонт: `docs/superpowers/specs/2026-07-30-library-reuse-architecture-design.md` (проект 1 выполнен, не задеплоен)
Статус: **v3 одобрен** — блокеры закрыты подтверждающим проходом, исполнение начато

## 0. Резюме

Сделать «переиспользуй, прежде чем создавать» **неотключаемым на границе API** и дешёвым для
агента с ограниченным контекстом:

1. детерминированный матчер семантических дубликатов (калиброванный на реальном каталоге);
2. `POST|GET /api/catalog/candidates` — компактный поиск кандидатов;
3. gate на **всех** путях создания активного компонента: `POST /api/components` и
   `POST /api/bundles/import`, с админским `force-new` через `reuseOverride`;
4. append-only аудит решений `catalog_reuse_decisions` + админское чтение;
5. селективные команды `driver.mjs catalog list|search|get`, `--intent/--force-new`;
6. единая политика авторинга для всех агентов (`AGENTS.md` + `CLAUDE.md` → канон).

Матчинг локальный, объяснимый, без эмбеддингов и без обращения к модели.

## 3. Архитектура

### 3.1 Корпус матчинга (`server/catalog/corpus.ts`)

Собирается **синхронно**, три источника:

1. **Активные публикации — из авторитетных таблиц.** `activeCatalogRows(db, designSystem)` +
   `JSON.parse(definition_meta)` (props/io/atomicLevel/scope/canonicalFor/description) +
   `headUsageCounts` + deprecated-статус. Исходник — `component_revisions.source` по
   `(component_id, rev)` активной публикации.
2. **Head-драфты** — компоненты без активной публикации, с фильтрами `c.deleted_at IS NULL` и
   `ds.retired = 0`. У драфта **нет** `definition_meta`, поэтому доступны только сигналы имени,
   исходника и `intent`: blocking-по-структурному-отпечатку против драфта не срабатывает.
   Это записано честно — драфт ловится шинглами, а не отпечатком.
3. **Кэш шинглов** — `component_fingerprints`, см. §3.6.

Из корпуса всегда исключается сам оцениваемый артефакт по `(designSystem, id)` (D4).

### 3.2 Отпечатки (`server/catalog/fingerprint.ts`)

Чистые функции, ноль обращений к БД:

- `propsSignature(schema)` — отсортированные имена свойств, required, примитив/enum-форма,
  политика `additionalProperties`; `default`/`description`/`title` отбрасываются.
- `ioSignature(events, slots)` — отсортированные события и именованные слоты.
- `sourceShingles(source)` — TSX-токены без комментариев, пробелов, литералов и локальных
  идентификаторов; k-шинглы (k=5), сравнение — Jaccard.
- `structuralFingerprint(meta)` — sha256 канонического JSON `{props, io, atomicLevel, scope}`.
  Точное равенство → blocking. **T0 обязана отдельно замерить число коллизий отпечатка на
  прод-дампе**: это единственный сигнал, блокирующий без порога, а `scope` сегодня пуст у всех
  записей, то есть фактически отпечаток опирается на `{props, io, atomicLevel}`.

**Инвариант неприменимого сигнала:** если сигнал **неприменим** к паре — оба сравниваемых
множества пусты **или** одна из сторон его не объявляет (драфт без `definition_meta`) — сигнал
исключается из суммы, а веса перенормируются на присутствующие.

Оба случая обязательны, и второй — не косметика. Без перенормировки 22 из 37 прод-компонентов
без событий и слотов получают +0.15 даром. А у драфта отсутствуют props, io, atomicLevel, scope
и description, то есть **0.65 весового бюджета из 1.00**: побайтово идентичный драфт-дубликат
набрал бы `source 0.20·1.0 + name 0.15·~0.7 = 0.35` — ниже даже review-порога, и фикс B4
переоткрылся бы молча (T0 этого не увидит, она калибруется на активном каталоге).
С перенормировкой тот же случай даёт ≈0.87 → blocking.

### 3.3 Скоринг (`server/catalog/matcher.ts` + `server/catalog/policy.ts`)

Сигналы — из спеки §3; **веса и пороги инъектируются** параметром `policy` и живут в
`policy.ts` с полем `policyVersion`. Стартовые значения — спековские:

```
props 0.25 · events+slots 0.15 · source-shingles 0.20 · name-tokens 0.15 ·
description/intent (IDF) 0.15 · same atomicLevel+scope 0.10
blocking ≥ 0.82 · review 0.65..0.8199
```

Независимо от score blocking дают: пересечение `canonicalFor`; равенство
`structuralFingerprint`. Deprecated/replaced возвращаются с `blocking:false` и
`recommendable:false`, если их активная замена присутствует **в корпусе** (не в усечённом до
`limit` ответе). Порядок: `score desc → id asc`, округление до 4 знаков перед сортировкой.

**IDF корпус-относителен**: публикация несвязанного компонента меняет IDF и может сдвинуть пару
через порог. Следствия — обязательные: фикстуры пинят собственный корпус описаний; в
аудит-записи сохраняется `policyVersion` (score невоспроизводим задним числом без него).

`reasons` — фиксированные шаблоны спеки §3. У blocking-кандидатов `propsDelta` —
имена добавленных/убранных/сменивших тип пропов (без схем и без значений).

### 3.4 Ревизия каталога

`catalogRevisionRows(rows)` — **чистая проекция** уже собранных строк (не второй проход по БД:
`libraryCatalog()` собирает всё через `assemble(db)` в одной транзакции, и повторный
`activeCatalogRows` + `JSON.parse` 115 мет ударил бы по read-model, который проект 1 только что
загнал под перф-гейт). Проекция: `{kind, designSystem, id, version, metaHash}`, где `metaHash` —
sha256 канонического JSON `{description, atomicLevel, scope, canonicalFor, replacement,
propsSignature, ioSignature}`. Считается по **нефильтрованному** каталогу.

Исключены намеренно: `headUsageCount`, `status.*`, `figma`, `preview`, `bundleUrl`.

Библиотека, `/catalog/candidates` и гейт потребляют одну функцию; тест сверяет побайтовое
равенство ревизий из библиотеки и из кандидатов на одной БД.

### 3.5 Gate создания (`POST /api/components`)

1. Дешёвые проверки до дорогого извлечения: аллоу-лист полей (+`intent`), слаг id, regex имени,
   `reserveHostPrimitiveName`, существование id и **глобальная** уникальность `name`
   (`components.name` UNIQUE — иначе `repo.create` кинет 409 уже после извлечения и после
   записи `blocked`-аудита), активность системы, права.
2. `intent` по фазе: `enforce` — обязателен (8–500 символов после trim, ≥1 токен вне stop-set
   `component|компонент|element|элемент|ui`); `shadow` — синтезируется из `name`, ответ несёт
   `warnings[]`, аудит помечается `intent_missing` вместе с идентификацией вызывателя
   (actor + user-agent), иначе «доля не ноль» не подсказывает, кого чинить.
3. `stageAndExtract()` (async): `<dataDir>/.staging/<uuid>/` → запись исходника →
   `checkSource`. Staging обязан лежать под корнем проекта, иначе материализованный TSX не
   разрешит `react`/`zod` из корневого `node_modules` (CLAUDE.md). Фиксированный корень
   `.staging/` + подметание сирот на старте — `finally` не спасает от SIGKILL при редеплое.
   Extraction failure остаётся 422 и **не** запускает матчинг на частичной мете (§9 спеки).
4. `matchAndDecide()` — **синхронный** блок `db.transaction(() => …)`, ни одного `await`
   (иначе bun:sqlite молча коммитит на первом await): сборка корпуса → матчинг → решение →
   вставка компонента и аудит-строки. Пересчёт именно здесь закрывает TOCTOU между конкурентными
   POST. `409` бросается **из** транзакции (тогда откат гарантирован), `blocked`-аудит пишется
   в `catch` снаружи.
5. Решения:
   - нет blocking → create + аудит `accepted_no_match`;
   - blocking, `enforce`, без override → `409 component_reuse_required`; ни строки компонента,
     ни durable-модуля; best-effort `blocked`-аудит вне транзакции;
   - blocking, `shadow` → компонент создаётся, аудит `would_block`, ответ несёт `warnings[]`;
   - валидный override (админ, `reason` 20–500, подтверждены все текущие blocking-ключи,
     `catalogRevision` совпал) → create + аудит `force_new` в той же транзакции;
   - `catalogRevision` не совпал → `409 catalog_changed` + свежие кандидаты;
   - исключение матчера → 5xx, компонента нет (§9 «never fails open»), тест на инъекцию сбоя.
6. Durable-материализация модуля на create **не выполняется вовсе**: `publishComponent`
   материализует заново из `repo.source(id)` (`routes/components.ts:71`), путь
   content-addressed. Это снимает и §9-требование про удаление staged-артефактов при откате.
7. `finally` — удаление staging во всех ветках.

Тело `409 component_reuse_required`:

```ts
{ error: "component_reuse_required", catalogRevision, decisionId, candidates: [...],
  retryable: false, resolution: "reuse" | "escalate", nextSteps: string[],
  repeatedAttempts: number | null,          // null, если аудит недоступен — не 0
  overrideTemplate: { catalogRevision, candidateKeys } }
```

`resolution` вычисляется **сервером** по детерминированному правилу поверх `propsDelta`:
`"reuse"`, если хотя бы у одного blocking-кандидата `propsDelta.removed` и
`propsDelta.typeChanged` пусты (кандидат способен выразить всё, что нужно вызывающему);
иначе `"escalate"`. `decisionId` позволяет сослаться на запись при эскалации к админу и
связывает 409 с агрегатами T10.

Уникальность `canonicalFor` внутри системы проверяется на create и на publish;
конфликт → `409 canonical_role_conflict`, обход — тот же админский override.

Режим гейта — параметр `HandlerOptions` (`server/main.ts:33`) с дефолтом `enforce` в коде и
переопределением из `REUSE_GATE` только на входе процесса (иначе тесты мутируют глобальный env
в общем процессе `bun test`). Прецедент `EASYUI_PUBLISH_GATES` (`readiness.ts:79`), выключенный
в проде с 2026-07-27 и не включённый до сих пор, — причина, по которой у выхода из shadow в §5
есть измеримый критерий, а решение эскалируется человеку.

### 3.6 Схема (миграция v20)

**`catalog_reuse_decisions`** — по §5 спеки плюс две колонки, без которых shadow ненаблюдаем:

```
id · actor_id · artifact_kind · artifact_id · design_system · source_or_doc_hash
catalog_revision · policy_version · gate_mode(shadow|enforce) · intent · candidates_json
decision(accepted_no_match | blocked | would_block | force_new | intent_missing)
reason · created_at
```

- **Без FK на `components(id)`**: `blocked`/`would_block` ссылаются на *предложенный* id, а
  миграции гоняют `PRAGMA foreign_key_check` (`migrations.ts:495`).
- Append-only через триггеры `BEFORE UPDATE/DELETE → RAISE(ABORT)`.
- `candidates_json` — компактные строки (id/score/blocking/reasons/propsDelta): имена пропов
  допустимы, значения props, исходники и токены — нет.
- Индексы: `(actor_id, created_at)`, `(artifact_id)`, `(decision)`.
- **Ретенция**: записи старше N дней удаляются джобом обслуживания (append-only запрещает
  UPDATE/DELETE из приложения — ретенция выполняется отдельным путём с явным логированием),
  иначе таблица растёт в проде бесконечно.

**`component_fingerprints` — строго content-addressed кэш шинглов, не источник истины:**

```
component_id · rev · source_sha256 (ключ) · shingles_json · updated_at
```

Промах кэша вычисляется на лету и пишется write-through внутри того же синхронного блока.
Props/io/структурные сигнатуры и описание **не хранятся** — они читаются из `definition_meta`
(активные публикации), поэтому расхождение двух источников истины невозможно по построению,
а restore (`routes/components.ts:165` → `repo.save` без `checkSource`), импортёр
(`importer.ts:239,250`) и прямые скрипты самозалечиваются.
Критерий T3: **корпус на БД без единой строки кэша идентичен корпусу после прогрева** — это и
есть тест на отсутствие fail-open.

### 3.7 Импорт бандла (T11)

Бандл не несёт `definition_meta` (`src/bundle/schema.ts:81-89`), а извлечение сегодня
происходит внутри `publishComponent` **после** `repo.create` (`importer.ts:250-251`). Поэтому
T11 добавляет `stageAndExtract()` **до** create и **переиспользует его результат** в
последующем `publishComponent` — иначе импорт 100 компонентов платит второй subprocess-спавн
(таймаут 10 с каждый) и время примерно удваивается.

- create-ветка проходит `matchAndDecide()` per-item; при blocking —
  `action: "error", detail: "reuse_blocked"` в отчёте (импорт по-элементный, запрос не роняется);
- аудит — с `actor = importerId` и синтезированным intent `imported from <origin>`;
  **в `mode=dry-run` аудит не пишется** (иначе любой пользователь бесконечно засоряет
  append-only таблицу и `repeatedAttempts` начинает врать);
- override — двухфазный поверх существующего `mode=dry-run`: dry-run возвращает per-item
  `reuse_blocked` с `candidateKeys` и `catalogRevision`; apply принимает `reuseOverride`
  **в теле** со списком подтверждённых item-id + `catalogRevision` + `reason`, и только от
  админа (сегодня маршрут — `requireUser`, `routes/bundles.ts:56`);
- в `shadow` импорт не отдаёт `reuse_blocked` (иначе shadow блокирует, то есть не shadow);
- ветка «существующий id → save+publish» гейт не проходит (это update, D4), но получает
  publish-предупреждение.

## 5. Порядок деплоя

1. **Отдельный релиз: проект 1 (library perf)** — он закоммичен, но не задеплоен; смешивать две
   несвязанные волны в одном релизе с одной точкой отката нельзя.
2. Волны 0–4 → `npm run verify` + `npm run e2e` + runtime `/verify`.
3. Деплой с `REUSE_GATE=shadow`.
4. **Критерий включения enforce разделён на два независимых вопроса** (иначе повторим историю
   `EASYUI_PUBLISH_GATES`, выключенных в проде с 2026-07-27):
   - *качество матчера* — из отчёта **T0**, а не из shadow-трафика: прод-создание компонентов
     идёт всплесками, за две недели создания может не быть вовсе. Критерий: отчёт принят,
     `policyVersion ≥ 1` (не provisional), доля пойманных известных дубликатов зафиксирована;
   - *безопасность включения* — из shadow, по конъюнкции: ≥ 2 недель наблюдения **И** ≥ 20
     решений от **≥ 2 разных акторов**, среди них ≥ 1 `would_block`; каждое `would_block`
     разобрано (легитимное срабатывание или ложное, закрытое фикстурой); `intent_missing` = 0
     среди последних K create.
   - Если K не достигнут за окно — решение эскалируется **человеку** (владельцу проекта) с
     отчётом: продлить окно либо включить enforce на доказательствах T0, приняв риск явно.
     Роль-без-имени («оркестратор волны») здесь недостаточна.
5. Переключение на `REUSE_GATE=enforce` отдельным деплоем; смена порогов после — версионное
   изменение политики (`policyVersion`) с отчётом и тестами.
6. Проект 3 стартует только после шага 5.

**Честная граница возможностей:** до бэкфилла `canonicalFor`/`scope` (проект 3) гейт ловит
структурные и исходниковые дубликаты, но не ролевые — blocking по канонической роли не может
сработать на каталоге, где это поле пусто у всех записей. Против драфтов не работает и
структурный отпечаток (у драфта нет `definition_meta`) — там остаются шинглы и имя.

Решения оркестратора по трём вопросам, поднятым T0 на уровень плана:

1. **Вырожденная коллизия отпечатка — исправлена** (доделано оркестратором в `fingerprint.ts`,
   зона T2 уже закрыта). Схема с пустым `properties` давала определённый отпечаток, поэтому два
   беспропсовых компонента блокировали друг друга **без порога**; на проде нашлась ровно такая
   пара (`yp-no-pay-card-info ↔ yp-separator`). Теперь пустая схема без событий и слотов
   равнозначна отсутствующей — сигнал неприменим, решение остаётся за порогом. Одного события
   или слота уже достаточно, чтобы отпечаток различал. После правки коллизий на проде — **0**;
   отчёт перегенерирован на исправленном ядре.
2. **Доминирование `source` 0.75 — принято.** Это замеренный выбор, а не предпочтение: с
   балансом спеки гейт ловил 7% дубликатов. Следствие честное — гейт стал детектором копипасты
   и одинаковой структуры. При поиске по одному `intent` сигнал исходника неприменим, и
   перенормировка оставляет имя с описанием, поэтому ранжирование discovery не страдает —
   **проверить приёмкой T4**.
3. **Ролевые дубликаты гейт не ловит** (из 9 известных пар аудита 2026-07-20 заблокирована 1,
   показана агенту 2). Это граница класса, а не дефект калибровки: без `canonicalFor` матчер
   видит только текстовое и структурное родство. Совпадает с §5 «честная граница возможностей»;
   закрывается бэкфиллом ролей в проекте 3.
