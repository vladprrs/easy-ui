# План: acceptance pipeline — фидбэк 2026-08-04

**Статус:** v3 после двух раундов Stage 2 (раунд 1: 3 линзы, 31/4; раунд 2 по переработанным местам: 2 линзы, 20/1, blocker'ов не осталось). Источник: `docs/EASYUI_ACCEPTANCE_PIPELINE_FEEDBACK_20260804.md`. Триаж обоих раундов — в конце файла.

## Контекст

`docs/EASYUI_ACCEPTANCE_PIPELINE_FEEDBACK_20260804.md` — фидбэк после первого боевого end-to-end переноса `pay-card-button` (12 cases) и `pay-payment-card` (49 cases, 2 shards) через контур case-set → accept → evidence → promote (план 2026-08-03, в проде, миграции v28, `EASYUI_ACCEPTANCE_MATRIX=1`). 8 проблем: 4×P0 (promote-линковка в CLI, promote отвергает pixel-strict, reuse вердиктов через границу политики, `--refresh failed` проигрывает impact), 4×P1 (ложный not-found, семантика padded reference, лимиты case-set/sparse families + multi-shard provenance, объём JSON), 1×P2 (уровни reuse).

### Корневые причины (верифицированы по коду, уточнены ревью)

- **P0-3/P0-4 — один узел, два дефекта** (`server/acceptance/orchestrator.ts`): порог per-case **входит** в `case_fingerprint` (через `casePolicyHash`), но (a) `forceOf("failed")` (:456-470) ищет провальный вердикт по **новому** fingerprint → после смены порога кэш пуст → форс молча снимается; (b) далее `carryBaselineCase` (`runner.ts:461-505`) переносит вердикт baseline-рана под новый fingerprint **не сравнивая** `casePolicyHash`. Плюс: `fingerprintOf` (`runner.ts:74-85`) не пробрасывает readiness-политику профиля (strict-ран получает `DEFAULT_READINESS_POLICY_HASH`), examples-путь использует заглушку `CASE_POLICY_HASH_V0`. **Уточнение ревью (C8):** дыра шире — `casePolicyHashOf` (`caseSets.ts:57-66`) хэширует профиль **из манифеста**, а не `policyId` рана, поэтому `--policy` не инвалидирует reuse и на case-set-пути; `expectedGeometry` и `cropLineage` случая не входят ни в `casePolicyHash`, ни в `caseFingerprint` — их смена даёт полный stale reuse.
- **P0-2 — эмерджентный отказ, promotion policy не существует**: кандидат при создании всегда штампуется `policyProfileHash(default-v1)` (`server/routes/acceptance.ts:235,245`), а `resolveAcceptanceRefs` (`server/components/promote.ts:126-128`) требует равенства хэша рана и кандидата → любой `pixel-strict-v1` ран падает `acceptance_run_mismatch`. RFC-инвариант: policy вне идентичности кандидата (не пересматривать).
- **P0-1 — чисто клиентский разрыв**: сервер уже принимает `candidateId`/`acceptanceRunId` (роут `components.ts:352-379`, тесты `component-promote.test.ts:310-393`), но `runPromote` в каноне `.claude/skills/author/driver.mjs:1993-2038` их не шлёт и флагов нет. Доп. пробел: одиночный `version()` DTO (`server/repos/components.ts:114`) не возвращает `candidateId`/`acceptanceRunId` (список versions — возвращает). Внимание (C4): `candidate.acceptanceRunId` — это **последний поставленный** ран (`repo.ts:275`), не «принятый»; источником автовыбора быть не может.
- **P1-5 — атрибуция фидбэка не совпадает с кодом**: `GET /components/:id` вообще не кэшируется (`cache.mjs classify:90-106`), «cached component list» не существует. Истинная причина неизвестна → волна начинается с расследования.
- **P1-6**: paint-канва = layout + 2×64px (`DEFAULT_PAINT_MARGIN_PX`, `service.ts:120`) × dsf; двухчастный контракт (padded reference vs `expectedGeometry`=layout root) существует, но неявен; `cropLineage.rect` не валидируется против размеров ассета — ловушка двойного crop.
- **P1-7**: `CASE_SET_MAX_DIMENSION_VALUES=32` (`src/acceptance/caseSetSchema.ts:45`) при `acceptanceMaxCasesPerRun=64` — единственная причина шардирования 49 cases; лимиты не видны в capabilities; валидация только через мутирующий PUT. **Уточнение ревью (C5/C16):** `coverageOf` (`caseSets.ts:294-296`) материализует полное декартово произведение без потолка — подъём лимита без потолка произведения опасен.
- **P1-9**: 1800 строк — `runView` (`server/routes/acceptance.ts:168-207`) инлайнит полные `gates[].metrics` всех failed cases; CLI спредит run в `--json` целиком.

## Ключевые решения

- **D-A (P0-2):** убрать hash-равенство; `acceptance_run_mismatch` = только «ран чужого кандидата»; новый предикат `run.policy_profile_id ∈ PROMOTION_POLICY_PROFILES` (оба встроенных профиля) → иначе новый `422 acceptance_policy_mismatch {runPolicyProfileId, allowed}`. Штамп кандидата не менять (информационный, задокументировать). `capabilities.acceptance.promotionPolicyProfiles` — по AC фидбэка, хотя сегодня предикат тавтологичен (C3: реестр содержит ровно эти два профиля, `startRun` отвергает чужие) — это задел под per-DS конфигурацию, тест ветки отказа — через инъекцию профиля. **Дополнение (C18):** promote сравнивает `run.policy_profile_hash` с текущим `policyProfileHash(ACCEPTANCE_POLICIES[id])`; расхождение (профиль ужесточался после рана) — не отказ, а warning в ответе + оба хэша в provenance опубликованной версии. Strict⇒weak получается автоматически.
- **D-B (P0-3/P0-4), переработано после ревью (C0/C12, C1, C2, C26):** fingerprint расслаивается на **три** слоя, а не два:
  - `frameFingerprint` — входы съёмки: candidateId, caseKey, propsHash, surface, readinessPolicyHash, rendererFingerprint;
  - `comparisonFingerprint` — входы **сравнения** (меняют метрики без пересъёмки): referenceAssetId, referenceSurface, referencePlacement, cropLineage (вкл. sourceSurface), maxDimensionDeltaPx, параметры нормализации канвы (margin, dsf);
  - `verdictPolicyHash` — входы **вердикта** (меняют решение без новых метрик): профиль/пороги (maxRawDiffPct, aa-бюджеты, severity), perCase-оверрайды, requireVisual, состав гейтов, geometry-допуски, expectedGeometry, allowPaintOverflow, expectedClip.
  - **Двухслойные поля (D1):** `expectedGeometry` входит **и** в comparison (он определяет `padTo` нормализации content-hug эталона в W5), **и** в verdictPolicy (допуски geometry). Инвариант: любое поле, участвующее в построении нормализованного эталона (padTo/placement/crop), обязано быть входом comparison, и при его смене визуальный гейт recompute'у не подлежит — только re-diff. Смена только `expectedGeometry` ⇒ comparison-промах ⇒ re-diff (для paint-манифестов это лишняя, но корректная работа).
  - **Тотальность разбиения (D3):** классификация полей по слоям — типизированное exhaustive-разбиение (`Record<PolicyOrCaseField, "frame"|"comparison"|"verdict">`), тест падает при появлении неклассифицированного поля; дефолт для нового поля — «frame» (перестраховка), никогда «нигде».
  - `caseFingerprint = hash({algo, frame, comparison, verdictPolicy})`; `CASE_FINGERPRINT_ALGO_VERSION` 5→6 (инвалидация прод-кэша — приемлема); examples-путь хэширует реальный профиль рана.
  - **Четыре пути reuse** (по месту промаха): caseFingerprint совпал → полный reuse; совпали frame+comparison, разошёлся verdictPolicy → **recompute** (чистый пересчёт по сохранённым `metrics_json`); совпал frame, разошёлся comparison → **re-diff** (перезапуск visual-гейта над сохранённым `paint.png` из CAS против нового эталона — без chromium); разошёлся frame → **recapture**. Правило перекрытия гейтов — по **дельте политики**, не по имени гейта (C26): отображение «поле effectivePolicy → затронутые гейты»; гейты вне дельты переносятся законно; затронутый непересчитываемый гейт (readiness, determinism и т.п.) → recapture, никогда не тихий перенос.
  - **Источник старой политики (D0/D14):** дельта вычислима только при известной старой effective-политике по значениям. v29 персистит канонизованный снимок effective verdict-policy случая (`verdict_policy_json`) рядом с хэшем; `verdict_policy_hash` — валидатор снимка. Правило: снимок отсутствует (legacy-строка, NULL) или hash не сходится ⇒ дельта неизвестна ⇒ **recapture, никогда не перенос** (это же — семантика NULL-слоёв v29 в carry, D17). Geometry-recompute считается от сырых `layoutBounds`/`paintBounds`/`effectSources` метрик, **не** от уже отфильтрованного старым допуском `overflow` (D0).
  - **Lookup (D6/D15):** для recompute — точный `caseResultForFrameComparison(frame, comparison, componentId)`; frame-only аксессор — для re-diff и `forceOf`. Кадр для re-diff — артефакт `paint.png` строки кэша с проверкой `artifactPresent`; отсутствует ⇒ recapture (`reuseReason:"recapture:frame_missing"`); «эталон добавлен к случаю со skipped visual» ⇒ re-diff, не recapture (D10).
  - **Алиасы (D16):** `policy.perCase`, адресующий случай с `aliasOf`, отвергается `422` — вердикт алиаса всегда идентичен цели; правило тестом.
  - **Progress (D9):** `reused` = только полный reuse по caseFingerprint; recompute/re-diff — отдельные счётчики (`verdictRecomputed`, `rediffed`); re-diff учитывается в EMA длительности как оплачиваемая работа; таблица «путь → счётчик → reuseReason» — в server-api.md.
  - **Артефакты (C2):** recompute/re-diff перезаписывают производные JSON-артефакты (`visual.json`/`geometry.json`) новыми записями CAS с `derivedFrom: <sha старого>`; байтовые (paint.png, diff.png при recompute) переиспользуются. Манифест evidence и содержимое артефактов пересчитанного случая обязаны быть согласованы (тест).
  - **Алгебра refresh (C1):** `effectiveRefresh = requestedRefresh ∪ impactRefresh`, считается на старте, персистится, печатается тройкой. Refresh получает **гранулярность** `frame | verdict`: `--refresh failed` = verdict-scope (форс инвалидации вердикта; кадр переиспользуется при совпавшем frameFingerprint — это делает достижимым «recapture=0»); `--refresh <ids>` и `--refresh all` = frame-scope (полная пересъёмка, текущая семантика); `--recapture` поднимает failed до frame-scope. `executeCase` принимает скоуп, а не булев `refresh`, и при verdict-скоупе не выключает frame-reuse. **Флейк-ретрай сохраняется (D4):** если у failed-случая нет дельты verdictPolicy/comparison относительно baseline (пересчитывать нечего), verdict-scope для него эскалируется до frame-scope — сегодняшняя способность «переснять упавшие» не теряется. **Отступление от AC фидбэка — зафиксировано (D19):** AC «recapture=0 невозможен без ошибки» переформулирован в «гарантируется переоценка (recompute/re-diff/recapture), не обязательно пересъёмка»; различие скоупов выводится в `--help`, человеческий вывод и server-api.md.
  - `forceOf("failed")` сначала смотрит вердикты baseline-рана (`repo.cases(baselineRunId)`), затем frame-lookup (C19 — не по caseFingerprint, иначе смена порога снова опустошает форс; C29 — фильтр по component_id, `ORDER BY last_used_at DESC LIMIT 1`).
  - `refresh_scope_empty` — предикат по **факту reuse** (C10): срабатывает только если при непустом explicit-скоупе хотя бы один случай отдан из кэша/carry и ни один не был переснят/пере-диффнут/пересчитан; первый ран с пустым кэшем проходит. **Механика (D2):** постановка (`POST /acceptance-runs`, 202) асинхронна — это не 422 на постановке, а **терминальный статус рана `error` + `statusReason:"refresh_scope_empty"`**, виден в run-view/summary, CLI завершает ненулевым кодом с объяснением. Статически вычислимые отказы скоупа (explicit id вне набора) остаются 422 на постановке, как сегодня.
  - Call-site постановки (D7): отпечатки случая считаются ровно одной функцией от effective policy рана — `createRun` и раннер используют общий расчёт; тест «case_fingerprint строки рана == строки результата».
- **D-C (P1-7):** поднять `CASE_SET_MAX_DIMENSION_VALUES` до 64 (тест-инвариант «≥ acceptanceMaxCasesPerRun»), все лимиты в capabilities, dry-run `POST /api/components/:id/case-sets/validate` + CLI `case-set validate` (локальный zod-parse + лимиты из кэшированных capabilities **до** сети, сервер — для db-зависимых проверок; C20). **Потолок произведения (C5/C16):** `expectedTuples ≤ 4096` проверяется перемножением длин **до** материализации → `422 case_set_coverage_too_large`, лимит в capabilities; `missingTuples` в ответе усечён. `caseSetGroup` **не строить**: с лимитом 64 семьи ≤64 cases однорановые; хвост >64 закрывает D-D.
- **D-D (P1-8):** promote принимает `acceptanceRunIds: string[]` (1..8, взаимоисключимо с одиночным); проверки: один кандидат, terminal pass, promotion-профиль, единый policy_profile_id, попарная дизъюнктность покрытия по ключу **(propsHash, surface)** — `capture` (viewport/dsf/theme) уровня набора, поэтому шардирование light/dark или по viewport'ам законно даёт одинаковые props и совпадающие caseId в разных наборах (D12); совпадение caseKey между наборами — warning, не ошибка (`422 acceptance_coverage_overlap` — только по (propsHash, surface)); опц. `expectedCases` (`422 acceptance_coverage_incomplete`). **Единый рендерер (C7):** v30 добавляет `acceptance_runs.renderer_fingerprint` (nullable, пишется новыми ранами); promote требует равенства у всех ранов набора, для legacy-строк с NULL проверка пропускается с warning. **Детерминизм (C7):** `acceptanceRunIds` сортируются при записи (`created_at, run_id`), legacy `acceptance_run_id` = первый элемент отсортированного списка — контракт задокументирован. Хранение: плоская TEXT-колонка `acceptance_run_ids` (JSON-массив, без FK — инвариант A9). **GC (C27):** `runIdsReferencedByPublishes()`/`isRunReferencedByPublish()` расширяются union'ом по `json_each(acceptance_run_ids)`.
- **D-E (P1-9), скорректировано (C11/C17/C24):** summary — серверный `?view=summary` с маркером `view:"summary"` в теле; CLI `--summary` строго **opt-in**, смысл `--json` **не меняется** (никакого условного переключения по вердикту); экономию контекста дают скиллы, переведённые на `--summary` в той же волне; link/receipt-store всегда строится из полного рана. Drill-down `accept-status --case <id>`.
- **Гейтинг возможностей (C23):** каждая новая клиент-видимая ручка получает флаг `capabilities.features.*`: `acceptanceSummaryView`, `caseSetValidate`, `acceptanceMultiRunPromote`; driver.mjs проверяет флаг до вызова (конвенция `runProvenance`/`runPromote`); для `?view=summary` клиент дополнительно проверяет маркер `view` в ответе (старый сервер молча игнорирует query).
