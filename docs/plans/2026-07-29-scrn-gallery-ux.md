# easy-ui — иерархические сценарии и вид «Сценарии» (по мотивам scrn.gallery)

**Версия плана: v1 (до ревью).** Дата: 2026-07-29.

## 1. Контекст и источник

Пользователь указал на [scrn.gallery](https://scrn.gallery) и, конкретно, на `https://scrn.gallery/app/wb-bank?tab=flows` — «нравится, как нарезаны сценарии и полнота». Изучение сделано по живым страницам (Playwright, скриншоты) **и** по их Nuxt-payload, поэтому известна не только картинка, но и модель данных.

**Что там устроено (факты, не пересказ маркетинга):**

- Каталог — четыре среза одной базы экранов: «Приложения», «Паттерны», «UI Элементы», «Сценарии». Сценарий — самостоятельная сущность с кросс-продуктовой таксономией (чипы «Онбординг», «Обзор и исследование», «Главный экран», «Переключение вида», «Добавление в корзину»).
- Страница приложения: шапка (лого, описание, «Июль 2026», ссылка в стор) + три вкладки-счётчика — «309 экранов», «82 сценария», «5 видео». Счётчик и есть заголовок вкладки: полнота декларируется числом.
- Вкладка «Сценарии»: слева дерево сценариев, справа вертикальная простыня секций «Название / N экранов», каждая — горизонтальная лента экранов. Действия на секции: ♥, «скопировать ссылку», «скачать».
- **Дерево — ядро находки.** `flow.parent` даёт вложенность до 4+ уровней: `Главный экран → Переводы и платежи → Перевод по номеру телефона → Квитанция о переводе`. Основная линия остаётся короткой (2–18 экранов), а полнота (модалки, edge cases, настройки, справки) уезжает в детей. Именно поэтому 82 сценария читаются, а не сливаются в кашу.
- Лайтбокс сценария: breadcrumb «WB Банк → Первый запуск», крупная лента, и при ховере на экране **подсвечиваются зоны-хотспоты с подписью цели** — «Текущий сценарий» либо имя другого сценария.
- Модель: `screen { type: image|video, tags, zones:[{x,y,width,height в %, screen_id, flow_id}] }`, `flow { name, parent, screens:[screen_id…], tags }`. Экраны **переиспользуются** между сценариями (у «Входа» и «Первого запуска» общий первый экран): сценарий — упорядоченная выборка, а не копия. Плюс `status {value: new|updated, until}` — бейдж протухает сам.

**Где мы сейчас.** `flowSchema` (`src/prototype/schema.ts:92`) плоский: `{id, name, description?, steps[{screenId, note?}]}`; лимиты `FLOWS_LIMIT=12`, `FLOW_STEPS_LIMIT=50`, `FLOW_TOTAL_STEPS_LIMIT=200`. В плеере сценарий выбирается `<select>`'ом (`src/player/ScenarioBar.tsx`), guided browse ходит по шагам через `?flow=&step=`. Вид `/p/:id/cjm` (`src/cjm/CjmView.tsx` + `lanesLayout.ts`) уже рисует **живые** экраны дорожками по флоу с рёбрами и легендой верификации. То есть у нас уже есть то, чего у scrn.gallery нет (живой рантайм, реальные хотспоты, verified-рёбра), и нет того, что у них есть: **иерархии, читаемой простыни по сценариям и подписей на зонах**.

**Терминологическая коллизия (важно для исполнителей).** Слово «сценарий» в кодовой базе занято дважды: `doc.flows` (пользовательские флоу, строки `player.scenario*`) и `prototype_scenarios` — записанные рекордером прогоны (`src/prototype/scenario.ts`, `src/player/scenarioPanel.tsx`, миграция v19). План **не переименовывает** ни то, ни другое; в коде новых модулей используем `flow*` для первого и `recordedScenario*` при упоминании второго.

## 2. Цели / не-цели

**Цели v1.**

1. Иерархия флоу (`parentId`) в документе + валидация + отображение деревом в плеере.
2. Вид «Сценарии»: простыня «секция на флоу» с лентой экранов, слева синхронизированное дерево.
3. Оверлей зон: подсветка хотспотов с подписью цели, включая «уводит в сценарий X».
4. Deep-link и копирование ссылки на конкретный флоу/шаг.
5. Счётчики полноты в шапке + два новых **info**-правила readiness.

**Не-цели v1 (осознанно).**

- Кросс-прототипный раздел «Сценарии» с фильтром по тегам — требует серверного индекса по всем прототипам и отдельной волны. Теги в схему кладём (T1), UI-срез — позже.
- Видео, ♥/коллекции, авторизация-гейт, «скачать сценарий архивом».
- Переезд с `doc.flows` на отдельную таблицу флоу. Флоу живут внутри документа-ревизии — так и остаётся, миграций БД в плане **нет**.
- Автогенерация дерева из записей рекордера (обсуждалось устно) — отдельная задача после T1.

## 3. Задачи

### T1 — Схема: иерархия и теги флоу

Владение: `src/prototype/schema.ts`, `src/prototype/validate.ts`, `src/prototype/__tests__/`, `docs/prototype-format.md`, `docs/server-api.md` (§capabilities), модуль capabilities на сервере.

Контракт (аддитивно, `version` документа остаётся `1`):

```ts
const flowSchema = z.strictObject({
  id: slugSchema,
  name: z.string().min(1).max(120),
  description: z.string().max(500).optional(),
  parentId: slugSchema.optional(),           // NEW
  tags: z.array(flowTagSchema).max(8).optional(), // NEW, slug-like, lowercase
  steps: z.array(flowStepSchema).min(1).max(FLOW_STEPS_LIMIT),
});
```

Правила валидации (в `refinePrototypeDoc`, рядом с существующими проверками флоу):

- `parentId` ссылается на существующий флоу того же документа; иначе issue на `["flows", i, "parentId"]`.
- Циклы запрещены (включая самоссылку) — обход с пометкой посещённых.
- Глубина ≤ `FLOW_DEPTH_LIMIT = 4` (корень = уровень 1).
- `flows[0]` (главный флоу, уже обязан начинаться со `startScreen`) обязан быть корневым: `parentId === undefined`.
- Порядок детей задаётся порядком в массиве `flows`; родитель обязан идти **раньше** ребёнка — это делает дерево читаемым в сыром JSON и упрощает построение без досортировки.

Лимиты: `FLOWS_LIMIT` 12 → **48**, `FLOW_TOTAL_STEPS_LIMIT` 200 → **600**. Обоснование: у иерархии без запаса по количеству нет смысла (у WB Банка 82 флоу); 48×средние 8 шагов ≈ 400. Перф-последствия закрывает T3 (ленивый рендер). Новые значения обязаны появиться в `GET /api/capabilities` (`limits.flows`, `limits.flowTotalSteps`, новые `limits.flowDepth`, `features.flowTree`) — значения импортируются из места enforce'а, без второго хардкода.

Обратная совместимость: документ без `parentId` ведёт себя ровно как сейчас (плоский список = все корни). Существующие прототипы не трогаем.

Done: `npm run verify` зелёный; unit-тесты на каждое правило (нет родителя / цикл / глубина 5 / ребёнок раньше родителя / главный флоу с parentId / 49 флоу); `docs/prototype-format.md` описывает поля и лимиты; `/api/capabilities` отдаёт новые значения.

### T2 — Дерево сценариев в плеере

Владение: `src/player/ScenarioBar.tsx` (+ тест), `src/app/strings/player.ts`, новый `src/player/flowTree.ts` (+ тест).

- `flowTree.ts` — чистая функция `buildFlowTree(flows): FlowNode[]` (узлы с `depth`, `children`, `path` предков) и `flowBreadcrumb(flows, id)`. Используется и T2, и T3 — единственный источник дерева.
- `<select>` заменяется на раскрывающийся список-дерево: отступ по `depth`, у каждого узла имя и «N экранов». Текущий узел подсвечен; над лентой шагов показывается breadcrumb предков (кликабельный).
- Плоский документ (нет ни одного `parentId`) должен выглядеть и работать как сейчас — дерево вырождается в список.
- Клавиатура и a11y: `role="tree"`/`treeitem` с `aria-level`, `aria-expanded`, стрелки вверх/вниз/влево/вправо, `aria-current` на активном.

Done: unit-тесты `buildFlowTree` (плоский, вложенный, порядок детей); тест ScenarioBar на выбор вложенного флоу и сохранение `?flow=&step=`; существующие тесты guided browse не изменены.

### T3 — Вид «Сценарии» (простыня)

Владение: `src/cjm/` (`CjmView.tsx`, `lanesLayout.ts` + тесты), `src/app/strings/cjm.ts`.

Не новый роут и не новый вью — **режим существующего `/p/:id/cjm`**, переключатель «Дорожки / Сценарии» в хроме, режим в query (`?view=flows`).

- Раскладка: вертикальный список секций по флоу в порядке дерева; заголовок секции — отступ по `depth`, имя, «N экранов», `description`, кнопка «Скопировать ссылку» (`?flow=<id>`), кнопка «Открыть в плеере».
- Тело секции — горизонтальная лента `CjmScreenTile` (те же живые тайлы, что в дорожках), клик по тайлу ведёт в плеер на этот шаг (`?flow=&step=`).
- Слева — дерево из `flowTree.ts`, синхронизированное со скроллом (IntersectionObserver, активная секция подсвечивается); клик скроллит к секции.
- **Ленивый рендер обязателен.** До 48 флоу × до 50 живых экранов рантайм не выдержит: тайлы монтируются только для секций в вьюпорте ±1, остальные — плейсхолдеры фиксированного размера (высота из `previewTileSizes[doc.device]`, чтобы скролл не прыгал). Горизонтальная лента внутри секции рендерит первые N=12 тайлов и досыпает по скроллу.
- Экран, не входящий ни в один флоу, попадает в существующую секцию «Не назначенные» (`UnassignedLane`).

Done: тест раскладки (порядок секций = порядок дерева, вложенность даёт отступ); тест ленивого монтирования (вне вьюпорта — плейсхолдер, без монтирования рантайма); e2e-проход по виду на фикстуре с вложенными флоу; ручная проверка скролла на прототипе с ≥20 флоу.

### T4 — Оверлей зон с подписью цели

Владение: `src/player/ScreenSurface.tsx` (+ тест), `src/prototype/navigationGraph.ts` (+ тест), `src/app/strings/player.ts`.

- Режим «Показать зоны» (тумблер в HUD плеера, по умолчанию выключен): поверх живого экрана рисуются рамки по DOM-геометрии элементов, у которых есть `navigate`-действие. Механика измерения переиспользует `measureMarkerRects`/`HighlightLayer` (уже используются панелью сценариев) — новой геометрии не изобретаем.
- Подпись у рамки: `→ <имя экрана>` плюс уточнение — «в текущем сценарии» (цель = следующий шаг активного флоу), «сценарий: <имя>» (цель = первый шаг другого флоу), иначе просто экран. Динамические таргеты (`dynamicSources` в `navigationGraph`) помечаются как «цель вычисляется» и рамкой без цели.
- `navigationGraph` расширяется до `edgesWithSource: Map<screenId, {elementKey, target}[]>` — сейчас там теряется, **какой элемент** даёт ребро; без этого подпись привязать не к чему. Существующие `edges`/`dynamicSources`/`verifyEdge` сохраняются как есть (их использует CJM).
- Только живой DOM плеера. В CJM-тайлах и в снимках оверлей не рисуется (тайлы масштабируются трансформом — координаты врут).

Done: unit-тест `edgesWithSource` (статический таргет, динамический, несколько действий на элементе); тест ScreenSurface на подписи трёх видов; тумблер не влияет на клики по прототипу (оверлей `pointer-events: none`).

### T5 — Ссылка на сценарий

Владение: `src/player/ShareDialog.tsx` (+ тест), `src/cjm/CjmView.tsx` (кнопка секции — граница с T3: T3 рисует кнопку, T5 владеет функцией построения URL), новый `src/player/flowLink.ts`.

- `flowLink.ts`: построение канонического URL `<origin><routeBase>/<screenId>?flow=<id>&step=<n>` и копирование в буфер с fallback (`navigator.clipboard` может отсутствовать в http-контексте).
- В `ShareDialog` — опция «ссылка на текущий сценарий» рядом с существующим шарингом прототипа; в дереве и в шапке секции — «Скопировать ссылку».

Done: unit-тест построения URL (с версией и без, с шагом и без); тест копирования с недоступным clipboard.

### T6 — Полнота

Владение: `src/capture/readiness.ts` (+ тест), `src/cjm/CjmView.tsx` (метаданные шапки — согласовать с T3), `docs/server-api.md` (§readiness).

- Шапка вида показывает «N экранов · N сценариев» (уже частично есть в `metadata`), плюс «M из N экранов покрыты сценариями».
- Два новых правила readiness уровня **info** (не blocking, не warning — иначе они сломают публикацию существующих прототипов): `flow/screen-uncovered` (экран не входит ни в один флоу) и `flow/no-description` (флоу без `description`).

Done: тест readiness на обоих правилах; проверка, что `publish` не блокируется (правила уровня info не попадают в `blocking`); `docs/server-api.md` описывает коды.

## 4. Порядок и параллельность

- Волна 1: **T1** (одна, все остальные зависят от схемы).
- Волна 2 (параллельно, зоны не пересекаются): **T2** (`src/player/ScenarioBar*`, `flowTree.ts`), **T4** (`ScreenSurface`, `navigationGraph`), **T5** (`ShareDialog`, `flowLink.ts`).
- Волна 3: **T3** (зависит от `flowTree.ts` из T2), затем **T6** (трогает шапку того же вью — последовательно, чтобы не конфликтовать в `CjmView.tsx`).

Коммитит оркестратор по зонам владения после независимой проверки done-критериев. Финальная приёмка: `npm run verify` + `npm run e2e` + runtime-прогон по `.claude/skills/verify/SKILL.md`. Фикстура с вложенными флоу добавляется в `test/fixtures/` в T1 и используется всеми последующими задачами.

## 5. Риски

| Риск | Митигация |
|---|---|
| Перф: 48 живых флоу в одном вью | Ленивый рендер обязателен (T3), плейсхолдеры фиксированной высоты; ручная проверка на ≥20 флоу |
| Поднятие лимитов ломает бюджеты сервера (размер тела ревизии `bodyMiB: 1`) | Проверить в T1, что 48×50 шагов + имена укладываются в лимит тела; при риске поднять только `FLOWS_LIMIT`, а `FLOW_TOTAL_STEPS_LIMIT` — на 400 |
| Коллизия слова «сценарий» с рекордером | Зафиксирована в §1; в UI строках различать «Сценарии» (флоу) и «Записи» (рекордер) — проверить, что строки не конфликтуют |
| Оверлей зон врёт на трансформированных тайлах | Только плеер, явно исключены CJM и снимки (T4) |
| Иерархию дорого набивать руками | Вне скоупа v1, но T1 сознательно кладёт `parentId` так, чтобы рекордер мог проставлять его автоматически |
