# easy-ui — иерархические сценарии и вид «Сценарии» (по мотивам scrn.gallery)

**Версия плана: v3.** Раунд 1: три линзы, 5 блокеров / 12 major — триаж в §8. Раунд 2: две линзы, 3 блокера / 9 major — триаж там же. Продуктовые решения пользователя внесены (§6). Дата: 2026-07-29.

## 1. Контекст и источник

Пользователь указал на [scrn.gallery](https://scrn.gallery), конкретно на `https://scrn.gallery/app/wb-bank?tab=flows` — «нравится, как нарезаны сценарии и полнота». Изучено по живым страницам (Playwright) **и** по их Nuxt-payload.

**Что там устроено:** каталог из четырёх срезов одной базы экранов; страница приложения с вкладками-счётчиками («309 экранов», «82 сценария», «5 видео»); вкладка «Сценарии» — дерево слева, простыня секций «Название / N экранов» с горизонтальной лентой экранов справа; лайтбокс с breadcrumb и подсветкой зон-хотспотов с подписью цели («Текущий сценарий» / имя другого сценария).

**Ядро находки — дерево.** `flow.parent` даёт вложенность до 4+ уровней (`Главный экран → Переводы и платежи → Перевод по номеру телефона → Квитанция о переводе`). Главная линия остаётся короткой (2–18 экранов), полнота уезжает в детей. Модель: `flow { name, parent, screens[] }`, экраны **переиспользуются** между сценариями — сценарий это упорядоченная **выборка**, а не копия.

**Где мы сейчас.** `flowSchema` (`src/prototype/schema.ts:92`) плоский; лимиты `FLOWS_LIMIT=12`, `FLOW_STEPS_LIMIT=50`, `FLOW_TOTAL_STEPS_LIMIT=200`. В плеере — `<select>` (`ScenarioBar.tsx:134`) и guided browse через `?flow=&step=`. `/p/:id/cjm` рисует живые тайлы дорожками с рёбрами и легендой верификации.

**Что даёт простыня поверх дорожек.** В дорожках якорные шаги ветки не имеют собственного тайла — `collectSegments` их пропускает (`lanesLayout.ts:184-195`), поэтому **прочитать ветку end-to-end сегодня невозможно**: видно только её отклонение от главной линии. Лента даёт полную последовательность каждого флоу. Рёбра и легенду верификации простыня не дублирует — они остаются в дорожках.

**Терминология (решено пользователем).** Флоу в UI — «Сценарии». Записи рекордера (`prototype_scenarios`, миграция v19) переименовываются в «**Проверки**»: `expectScreen`/`expectText`/`expectDisabled` — это assertions. Схема, API и имена таблиц не меняются; в коде — `flow*` против `recordedScenario*`.

## 2. Ключевое решение: дочерние флоу — не дорожки и не цепочки

Центральный контракт плана. Дочерний флоу (`parentId !== undefined`) — это **выборка** экранов, а не связная ветка, заякоренная в главную линию. Из этого следуют четыре освобождения и одна нормировка.

**Что освобождается для флоу с `parentId`:**

| Правило | Где | Почему освобождается |
|---|---|---|
| `adjacent main-flow anchors must be consecutive in the forward direction` (**error**) | `schema.ts:188-199` | Правило существует ради выразимости геометрии дорожек. Точная механика: оно срабатывает только когда **два соседних шага** — оба якоря главной линии с неконсекутивными индексами. Дочерний флоу `[main-A, main-D]` его нарушает; `[main-A, x, y, main-D]` — нет |
| `flow step is not connected to the previous step by a navigate action` (warning) | `validate.ts:536-538` | Выборка не обязана быть связной цепочкой `navigate`-рёбер: между шагами N и N+1 в реальном прототипе стоят промежуточные экраны, которых в выборке нет. Иначе **каждый разрыв** давал бы warning |
| `flow has a single step` (warning) | `validate.ts:530` | Канонический лист дерева («Квитанция о переводе») — ровно один экран. Иначе **каждый лист** давал бы warning |
| `flow step note on a main-flow anchor is not displayed` (warning) | `validate.ts:532-535` | Снимается **для всех не-первых флоу**, а не только для дочерних: премиса warning'а («у якоря нет своего тайла») перестаёт быть верной, как только режим «Сценарии» рендерит якорные шаги — а он становится дефолтным (§6) |

Почему это критично, а не косметика: `server/readiness.ts:216-218` красит гейт `schema` `pass→warn` от **любого** неархитектурного warning'а `validatePrototype`, и при `EASYUI_PUBLISH_GATES=schema:warn` это блокирует публикацию. Без освобождений прототип с деревом гарантированно уезжает в `schema: warn` — ровно тот эффект, из-за которого §4 отказался вводить новые readiness-правила.

**Что нормируется:** фильтр «дорожки только по корневым флоу» применяется **исключительно к построению геометрии** (`main`/`branches`/`branchSegments`/`gapWidths`/`columns`/`lanes`). `assigned`/`unassigned` (`lanesLayout.ts:224-225`) считаются по `doc.flows` **целиком**. Иначе экран, живущий только в дочернем флоу, попадёт в секцию «Вне сценариев» (`CjmView.tsx:80-96`) — прямая ложь, — а метрика покрытия (§4) станет тем хуже, чем аккуратнее автор разложил детали по детям. Реализация: один `const rootFlows = doc.flows.filter((f) => f.parentId === undefined)` сразу после проверки на `undefined`, и все места **кроме** `assigned` читают его; иначе индексы `branchSegments` (`lanesLayout.ts:117,175-178,191-193`) разъедутся молча. `main!` не станет `undefined`: правило «`flows[0]` обязан быть корневым» гарантирует минимум один корень.

## 3. Безопасность отката: двухфазный деплой

`storedPrototypeDocSchema` — `z.strictObject` (`schema.ts:214`), и `parseStoredPrototypeDoc` превращает отказ в `422 invalid_stored_revision` **на чтении** (`server/repos/prototypes.ts:43-46`). Значит откат волны способом, который сам `.claude/skills/deploy/SKILL.md` называет первоклассным (revert + push → предыдущий образ), сделает **любую** ревизию с `parentId` нечитаемой: сначала окирпичится acceptance-прототип, затем всё, что успели наавторить пользователи. Тест вакуумности покрывает только прямое направление.

**Решение — два релиза:**

- **R1 (T0):** stored-ветка схемы флоу становится толерантной к неизвестным ключам (`z.looseObject` / catchall только для `storedPrototypeDocSchema`; input-ветка остаётся строгой). Ничего не пишет и не показывает. Деплоится отдельно и первой.
- **R2 (T1–T4):** запись `parentId` и весь UI. Откат R2 возвращает образ R1, который документы с `parentId` читает (игнорируя поле — флоу выглядят плоскими), а не роняет.

Никакой записи `parentId` в прод до того, как R1 выкачен и проверен.

## 4. Цели / не-цели

**Цели.** (1) `flow.parentId` + валидация + освобождения §2. (2) Обратный индекс «экран → в каких сценариях участвует» — работает уже на **сегодняшних плоских** флоу. (3) Режим «Сценарии» в `/p/:id/cjm` (дефолтный, §6) с деревом слева; ленивое монтирование, распространённое **и на существующие дорожки**. (4) Дерево вместо `<select>` в плеере. (5) Оверлей зон с подписью цели. (6) «Сценарии» / «Проверки». (7) Авторская поддержка иерархии + один переавторенный прототип.

**Не-цели (с обоснованием).**

- **`flow.tags`** — потребителя в этой волне нет, а поле навсегда входит в strict-схему, JSON Schema, закоммиченный OpenAPI и diff. Теги уровня прототипа уже есть (миграция v16).
- **Правила readiness** (`flow/screen-uncovered`, `flow/no-description`). `READINESS_GATE_IDS` закрыт (`server/readiness.ts:30-41`), статусы — `pass|warn|fail|unknown`, уровня `info` нет; новый gate тянет `contracts.ts` + регенерацию OpenAPI + `contract.test.ts`. А warning из `validatePrototype` перекрасил бы гейт `schema` у большинства прод-прототипов. Метрику покрытия считаем в UI из `CjmLayout.unassigned`.
- **`flowLink.ts` и `ShareDialog`.** `exchangeShareToken` (`server/routes/share.ts:39-51`) пробрасывает в 303 только `mobile`, теряя `flow`/`step`. «Скопировать ссылку» в v1 — внутренний URL.
- Кросс-прототипный раздел «Сценарии», видео, коллекции, статусы `new/updated`, переезд флоу в таблицу, автогенерация дерева из рекордера.

### T1a — Схема и `flowGraph`

Владение: `src/prototype/schema.ts`, `src/prototype/validate.ts`, новый `src/prototype/flowGraph.ts`, `src/prototype/__tests__/{schema-flows,validate}.test.ts`, `src/cjm/lanesLayout.ts` + `src/cjm/lanesLayout.test.ts`, `src/editor/docDiff.ts`.

Схема (аддитивно, `version` = `1`; `tags` не вводим): `parentId: slugSchema.optional()`. Локальный generic `refinePrototypeDoc` (`schema.ts:147-151`) типизирует флоу как `{id, steps}[]` — расширить, иначе не затайпчекается.

Правила:
- `parentId` ссылается на существующий флоу; issue path — `["flows", i, "parentId"]` (по нему `server/readiness.ts` строит навигацию UI);
- **родитель раньше ребёнка в массиве** — единственное нормативное правило порядка. Оно же даёт ацикличность (отношение `parent: i → j < i` — лес по построению) и вычисление глубины одним прямым проходом. Отдельных проверок на цикл и самоссылку нет: они избыточны и давали бы по три перекрывающихся issue на одно нарушение;
- глубина ≤ `FLOW_DEPTH_LIMIT = 4`, где **корень = уровень 1** (пример из §1 — ровно 4 уровня). Семантику зафиксировать в `docs/server-api.md`, значение уезжает в публичный `/api/capabilities`;
- `flows[0]` обязан быть корневым;
- освобождения §2 — четыре штуки, каждое отдельным тестом.

Defensive-требования (иначе каскад дублирующих issue): висячий `parentId` → флоу трактуется как корень, второй issue про глубину **не** добавляется; карта `id → index` фиксирует первое вхождение (дубликаты `id` `schema.ts:163` только репортит, но не устраняет); при нарушении порядка проверка глубины для поддерева подавляется. Аргумент про O(n²) несостоятелен при `n ≤ 24` — оптимизировать нечего, важна простота.

`FLOWS_LIMIT` 12 → **24** здесь же: на ширину грида дорожек это не влияет (дочерние флоу — не дорожки, §2), а acceptance-критерий §7 иначе упирается в лимит, снимаемый последней задачей. `FLOW_TOTAL_STEPS_LIMIT` остаётся 200 до T4.

`src/prototype/flowGraph.ts` — единственный источник производных структур: `buildFlowTree` (узлы с `depth`, `children`, `path`; порядок обхода — **явный DFS** по порядку массива, поскольку правило «родитель раньше ребёнка» не пиннит порядок поддеревьев), `flowBreadcrumb`, **`screenFlowIndex(doc)` → `Map<screenId, {flowId, stepIndex}[]>`** — обратный индекс переиспользования, работающий на плоских флоу.

`lanesLayout.ts` — фильтр `rootFlows` строго по контракту §2. `docDiff.ts:89-106` учится показывать изменение `parentId` и **смену главного флоу** (правило порядка заставляет двигать элементы массива, и `flows[0]` легко сдвинуть случайно — правило «корневой» этого не ловит, корневой ≠ главный).

Done: `npm run verify` зелёный; тест на каждое правило и каждое освобождение; **негативный тест anchor-adjacency**: фикстура с соседними неконсекутивными якорями падает в корневом флоу и проходит в дочернем; тест «`unassigned` не включает экраны дочерних флоу»; unit-тесты `flowGraph` (DFS-порядок, breadcrumb, обратный индекс на плоских и вложенных); тест вакуумности — все `test/fixtures/*.json` проходят `storedPrototypeDocSchema`.

### T4 — Подъём `FLOW_TOTAL_STEPS_LIMIT`

Владение: `src/prototype/schema.ts` (константа), `server/routes/meta.ts`, `server/contract.test.ts`, `docs/server-api.md`, `test/fixtures/flows-perf.json`.

Выполняется после T2a/T2b. `FLOW_TOTAL_STEPS_LIMIT` 200 → **320** (`FLOWS_LIMIT` поднят в T1a). Не 600: при 48 флоу ширина грида дорожек (`columns = main.steps + Σ gapWidths`, `lanesLayout.ts:230`) уходит к ~550 колонкам × 584 px ≈ 320 000 px, а `CjmEdgesOverlay` даёт O(N) `getBoundingClientRect` на каждый из N колбэков.

Порядок внутри задачи, чтобы не было круговой зависимости (фикстуру новых лимитов нельзя засеять, пока константа не поднята — `POST /api/prototypes` валидирует): сначала константа, затем расширение `flows-perf.json`, затем прогон счётчиков T2a на новой фикстуре. Гейт — кривая роста из unit-теста масштабирования, а не абсолютное время.

Бюджет тела считаем честно: связывающее ограничение — **не шаги** (320 шагов ≈ 10 KB против `MAX_JSON_BODY_BYTES = 1 MiB`, `server/http.ts:39`), а экраны: реальный экран стоит 1.3–4.7 KB (`checkout.json` 1321 B/экран, `scale-demo.json` 4692), 318 B/экран в `flows-perf.json` — синтетика. Тест бюджета собирается из реалистичного экрана. `SCREENS_LIMIT` в коде нет — лимит тела и есть де-факто лимит экранов; вводить ли явный лимит вместо голого `413 payload_too_large` — решение внутри T4.

## 6. Продуктовые решения (ответы пользователя)

1. **Дефолтный режим `/p/:id/cjm` — «Сценарии».** Полнота читается из ленты; дорожки становятся advanced-видом отклонений (`?view=lanes`). Это делает T2a (ленивость дорожек) обязательным до смены дефолта — иначе дефолтный вход станет тяжелее нынешнего.

## 7. Порядок, деплой, приёмка

**Релизы:** R1 = T0 (толерантная stored-схема, деплой и проверка в проде). R2 = T1a → T1b → T2a → T2b → T3 → T4, последовательно.

Оркестратор независимо проверяет done-критерии и коммитит по зонам. Финальная приёмка: `npm run verify` + `npm run e2e` + runtime-прогон по `.claude/skills/verify/SKILL.md`.

**Про «перф до push в main».** Формулировка v2 создавала ложное чувство гейта: `.github/workflows/build-image.yml:3-5` триггерится на push в `main` **независимо** от `ci.yml`, красный CI сборку образа и автодеплой не блокирует. Либо в рамках волны добавляется зависимость/branch protection, либо честно: перф-проверка — **локальный pre-push шаг оркестратора**, и он обязателен, потому что регрессия CJM едет в SPA-бандле, а первоклассного отката нет.

**Acceptance волны — постдеплойный шаг:** прод валидирует на записи, значит переавторить прототип трёхуровневым деревом можно только после выката R2. Инструментов достаточно: `driver.mjs` умеет `get <kind> <id>` (`:855-858`, тянет документ через `/prototypes/:id/draft`) и запись обратно через `prototype <doc.json>`. Первым берётся одноразовый прототип, не боевой.
