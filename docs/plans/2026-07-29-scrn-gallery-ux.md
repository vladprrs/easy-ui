# easy-ui — иерархические сценарии и вид «Сценарии» (по мотивам scrn.gallery)

**Версия плана: v4.** Три раунда адверсариального ревью (7 линз): раунд 1 — 5 блокеров / 12 major, раунд 2 — 3 / 9, раунд 3 — 6 / 11. Триаж — §9. Дата: 2026-07-29.

## 1. Контекст и источник

Пользователь указал на [scrn.gallery](https://scrn.gallery), конкретно на `https://scrn.gallery/app/wb-bank?tab=flows` — «нравится, как нарезаны сценарии и полнота». Изучено по живым страницам (Playwright) **и** по их Nuxt-payload.

**Что там устроено:** каталог из четырёх срезов одной базы экранов; страница приложения с вкладками-счётчиками («309 экранов», «82 сценария», «5 видео»); вкладка «Сценарии» — дерево слева, простыня секций «Название / N экранов» с горизонтальной лентой экранов справа; лайтбокс с breadcrumb и подсветкой зон-хотспотов с подписью цели.

**Ядро находки — дерево.** `flow.parent` даёт вложенность до 4+ уровней (`Главный экран → Переводы и платежи → Перевод по номеру телефона → Квитанция о переводе`). Главная линия остаётся короткой, полнота уезжает в детей. Модель: `flow { name, parent, screens[] }`, экраны **переиспользуются** между сценариями — сценарий это упорядоченная **выборка**, а не копия.

**Где мы сейчас.** `flowSchema` (`src/prototype/schema.ts:92`) плоский; лимиты `FLOWS_LIMIT=12`, `FLOW_STEPS_LIMIT=50`, `FLOW_TOTAL_STEPS_LIMIT=200`. В плеере — `<select>` (`ScenarioBar.tsx:135-146`) и guided browse через `?flow=&step=`. `/p/:id/cjm` рисует живые тайлы дорожками с рёбрами и легендой верификации.

**Что даёт простыня поверх дорожек.** В дорожках якорные шаги ветки не имеют собственного тайла — `collectSegments` их пропускает (`lanesLayout.ts:184-195`), поэтому **прочитать ветку end-to-end сегодня невозможно**. Лента даёт полную последовательность каждого флоу. Рёбра и легенду верификации простыня не дублирует.

**Терминология (решено пользователем).** Флоу в UI — «Сценарии». Записи рекордера (`prototype_scenarios`, миграция v19) — «**Проверки**»: `expectScreen`/`expectText`/`expectDisabled` это assertions. Схема, API и имена таблиц не меняются.

## 2. Фактическая база: флоу сегодня никто не пишет

Проверено по `.backups/prod-v2-20260729/full-export.zip` и `test/fixtures/`:

- **0 из 13 прод-прототипов** содержат `doc.flows`;
- 2 из 9 фикстур (`branching-checkout` — 3 флоу, `flows-perf` — 12 синтетических);
- UI редактирования флоу не существует (`grep flows src/editor/*.tsx` пуст), скиллы автора о флоу молчат — флоу пишутся руками в JSON через API.

Три следствия, которые пронизывают весь план:

1. **Вид по умолчанию обязан быть осмысленным без флоу** (§6.1). Иначе смена дефолта на «Сценарии» даёт пустой экран на всём сегодняшнем проде.
2. **Ценность волны отложена до авторинга.** Обратный индекс (`screenFlowIndex`) и ленивость дорожек — единственные части, работающие в день выката на существующих данных.
3. **Acceptance-критерий (§8) — не формальность, а единственная проверка, что фича вообще применима.**

## 3. Ключевое решение: дочерние флоу — не дорожки и не цепочки

Дочерний флоу (`parentId !== undefined`) — это **выборка** экранов, а не связная ветка, заякоренная в главную линию.

**Что освобождается:**

| Правило | Где | Область освобождения | Почему |
|---|---|---|---|
| `adjacent main-flow anchors must be consecutive` (**error**) | `schema.ts:188-199` | только `parentId !== undefined` | Правило существует ради выразимости геометрии дорожек. Механика: срабатывает, только когда **два соседних шага** — оба якоря главной линии с неконсекутивными индексами (`[main-A, main-D]` нарушает; `[main-A, x, y, main-D]` — нет) |
| `flow step is not connected to the previous step by a navigate action` (warning) | `validate.ts:536-538` | только `parentId !== undefined` | Выборка не обязана быть связной цепочкой рёбер — иначе **каждый разрыв** давал бы warning |
| `flow has a single step` (warning) | `validate.ts:530` | только `parentId !== undefined` | Канонический лист дерева — один экран; иначе **каждый лист** давал бы warning |
| `flow step note on a main-flow anchor is not displayed` (warning) | `validate.ts:532-535` | **все не-первые флоу**, включая плоские | Премиса («у якоря нет своего тайла») перестаёт быть верной, как только режим «Сценарии» рендерит якорные шаги. В `?view=lanes` note по-прежнему не виден — это принимается как осознанная неточность |

Почему критично: `server/readiness.ts:215-218` красит гейт `schema` `pass→warn` от **любого** неархитектурного warning'а, и при `EASYUI_PUBLISH_GATES=schema:warn` это блокирует публикацию.

**Принимаемый компромисс:** `parentId` становится способом легализовать «срез» `[main-A, main-D]`, обходя error-правило, и одновременно убрать флоу из дорожек. Это осознанно: дочерний флоу и есть срез. Записать в `docs/prototype-format.md`.

**Компенсация потери сигналов связности.** Для дочернего флоу снят warning связности, и рёбер с `verified` для него не строится (он не дорожка), а легенда есть только в дорожках (`CjmView.tsx:181-185`). Автор остался бы без единого индикатора проходимости. Поэтому T2b рисует **per-step метку верификации** в ленте — данные уже есть (`verifyEdge`).

**Нормировка:** фильтр «дорожки только по корневым флоу» применяется **исключительно к геометрии** (`main`/`branches`/`branchSegments`/`gapWidths`/`columns`/`lanes`). `assigned`/`unassigned` (`lanesLayout.ts:224-225`) считаются по `doc.flows` **целиком** — иначе экран из дочернего флоу попадёт в «Вне сценариев», а метрика покрытия инвертируется. Реализация: один `const rootFlows = …` сразу после проверки на `undefined`; все места кроме `assigned` читают его, иначе индексы `branchSegments` (`:117,175-178,191-193`) молча разъедутся.

## 4. Безопасность отката: авторские правила уходят из stored-ветки

`refinePrototypeDoc` навешан `.superRefine()` на **обе** ветки — `inputPrototypeDocSchema:207` и `storedPrototypeDocSchema:217`, а `.max(FLOWS_LIMIT)` живёт в общем `prototypeDocShape:142`. То есть **на чтении** каждой ревизии (`server/repos/prototypes.ts:44`) исполняются и геометрические правила, и лимиты. Откат волны на предыдущий образ поэтому ломает документы тремя независимыми способами:

1. неизвестный ключ `parentId` (strict);
2. разрешённая §3 выборка `[main-A, main-D]` — по anchor-adjacency;
3. 13+ флоу после подъёма `FLOWS_LIMIT` (T1) и 201+ шагов после T4 — по лимитам.

Митигация v3 («stored игнорирует неизвестные ключи») лечила только первый и давала ложное чувство безопасности. Хуже: `restore` переписывает новую ревизию из **распарсенного** документа (`server/repos/prototypes.ts:190-194`), поэтому strip-вариант молча и навсегда расплющил бы иерархию, а loose-вариант дал бы 422 на каждом сохранении (обратно в строгий `inputPrototypeDocSchema`).

**T0 (релиз R1) в правильной форме:**

- stored-ветка перестаёт исполнять **авторские** правила и лимиты: они становятся input-only. Stored-парс проверяет только структурные инварианты, на которые опирается код (типы, существование `startScreen`/`screenId`);
- `parentId: slugSchema.optional()` добавляется в `flowSchema` **обеих** веток — чистое аддитивное поле, без правил, без UI, без потребителей.

Тогда откат читает, сохраняет, восстанавливает и round-trip'ит без потерь, и это rollback-safe для **всей** волны разом, включая подъём лимитов в T1/T4. Цена, которую надо назвать честно: `meta.ts:97` строит JSON-схему из input-ветки, `server/openapi.json` её инлайнит, `verify:openapi` — байт-сравнение, поэтому регенерация контракта переезжает в T0.

Побочно закрывается `server/bundle/importer.ts:363` — единственное место, где **сохранённая** head-ревизия валидируется строгой input-веткой (на откате давало бы `action:"error"` в отчёте импорта).

## 5. Цели / не-цели

**Цели.** (1) `flow.parentId` + валидация + освобождения §3. (2) `screenFlowIndex` — обратный индекс «экран → в каких сценариях участвует», работает на сегодняшних плоских флоу. (3) Режим «Сценарии» в `/p/:id/cjm` (дефолтный) с деревом слева; ленивое монтирование в обоих режимах. (4) Дерево вместо `<select>` в плеере. (5) Оверлей зон с подписью цели. (6) «Сценарии» / «Проверки». (7) Авторская поддержка иерархии + один переавторенный прототип.

**Не-цели (с обоснованием).** `flow.tags` — потребителя в волне нет, а поле навсегда входит в strict-схему, JSON Schema и OpenAPI. Правила readiness — `READINESS_GATE_IDS` закрыт (`server/readiness.ts:30-41`), уровня `info` нет, а warning перекрасил бы гейт `schema`; метрику покрытия считаем в UI. `flowLink.ts`/`ShareDialog` — `exchangeShareToken` (`server/routes/share.ts:39-51`) пробрасывает в 303 только `mobile`. Кросс-прототипный раздел «Сценарии», видео, коллекции, статусы `new/updated`, переезд флоу в таблицу, автогенерация дерева из рекордера.

## 6. Продуктовые решения

1. **Дефолтный режим `/p/:id/cjm` — «Сценарии»** (решение пользователя), дорожки — `?view=lanes`. **Обязательный контракт:** при `layout.linear` (документ без `doc.flows` — сегодня это 100 % прода, §2) режим «Сценарии» показывает ту же линейную ленту `Экраны CJM`, что и сейчас (`CjmView.tsx:140-145`), а переключатель скрыт. Без этого дефолт даёт пустой экран на всём проде.
   Уточнение обоснования: ленивость T2a удешевляет не дефолт, а advanced-вид; для дефолта тот же механизм должен прийти из T2b, поэтому T2a обязан вынести ленивую обёртку в переиспользуемый компонент.
2. **Записи рекордера в UI — «Проверки».**
3. Кандидат на переавторинг для acceptance — **`magnit-loyalty-entry-flow`** (6 экранов, «выпуск бонусной карты из Pay»; решение пользователя 2026-07-29). Реальный продуктовый флоу, режется на главную линию и дочерние ветки без синтетики. Acceptance делается на копии-одноразовике, боевой прототип не трогаем.

- **родитель раньше ребёнка в массиве** — единственное нормативное правило порядка; оно же даёт ацикличность (отношение `parent: i → j < i` — лес по построению) и глубину одним проходом. Отдельных проверок на цикл и самоссылку нет;
- глубина ≤ `FLOW_DEPTH_LIMIT = 4`, **корень = уровень 1** (пример §1 — ровно 4). Семантику зафиксировать в `docs/server-api.md`: значение уезжает в публичный `/api/capabilities`;
- `flows[0]` обязан быть корневым;
- освобождения §3 — четыре штуки, каждое отдельным тестом.

Defensive: висячий `parentId` → трактуется как корень, второй issue про глубину не добавляется; карта `id → index` фиксирует первое вхождение (дубликаты `schema.ts:163` только репортит); при нарушении порядка проверка глубины поддерева подавляется. Про O(n²) при `n ≤ 24` оптимизировать нечего — важна простота.

`FLOWS_LIMIT` 12 → **24** здесь же. Корректное обоснование (v3 приводил ложное): ширина грида = `main.steps.length + Σ insertedColumns`, где `gapWidths` берёт **максимум** по ветвям на каждый gap (`lanesLayout.ts:118-127,230`) — она ограничена `FLOW_TOTAL_STEPS_LIMIT` и `FLOW_STEPS_LIMIT`, а не числом флоу. Даже 24 **корневых** флоу грид не расширяют; растёт только число строк-дорожек, что для ленивости T2a безразлично.

`src/prototype/flowGraph.ts`: `buildFlowTree` (узлы с `depth`, `children`, `path`; порядок — **явный DFS** по массиву), `flowBreadcrumb`, **`screenFlowIndex(doc)` → `Map<screenId, {flowId, stepIndex}[]>`**.

`lanesLayout.ts` — фильтр `rootFlows` строго по §3. `docDiff.ts:89-106` учится показывать `parentId` и **смену главного флоу** (правило порядка заставляет двигать элементы массива, и `flows[0]` легко сдвинуть случайно).

## 8. Порядок, деплой, приёмка

**R1 = T0**, отдельным релизом, с позитивной проверкой в проде (§7 T0). **R2 = T2a → T1 → T1c → T2b → T3 → T4.** T2a идёт первой: она независима от схемы, снимает существующий перф-долг и даёт переиспользуемую ленивую обёртку для T2b. (В v3 §5 и §7 противоречили друг другу — исправлено.)

**Откат.** `.claude/skills/deploy/SKILL.md` прямо говорит: «**No first-class rollback** — point the compose file at a known-good image tag … or revert the offending commit and push» (v3 цитировал это неверно в обе стороны). Что делает откат дешёвым здесь: **в волне нет миграций БД** (флоу живут в JSON-колонке ревизии), поэтому оговорка скилла про восстановление тома неприменима, и откат = re-point на `ghcr.io/vladprrs/easy-ui:<sha T0>`.

**Про «перф до push».** `.github/workflows/build-image.yml:3-5` триггерится на push в `main` **независимо** от `ci.yml`: красный CI сборку образа и автодеплой не блокирует. Либо в рамках волны добавляется зависимость/branch protection, либо честно — перф-проверка это **локальный pre-push шаг оркестратора**, обязательный, потому что регрессия CJM едет в SPA-бандле.

**Acceptance — постдеплойный шаг:** прод валидирует на записи, значит переавторить прототип трёхуровневым деревом можно только после выката R2. Инструментов достаточно: `driver.mjs get <kind> <id>` (`:855-858`, тянет документ через `/prototypes/:id/draft`) и запись обратно через `prototype <doc.json>`. Первым берётся одноразовый прототип, не боевой. С учётом §2 (0 из 13 прод-прототипов имеют флоу) это единственная проверка применимости фичи.
