# easy-ui — иерархические сценарии и вид «Сценарии» (по мотивам scrn.gallery)

**Версия плана: v2.** Раунд 1 адверсариального ревью: три линзы (корректность контрактов, ценность/скоуп, риски/перф), 5 блокеров и 12 major — триаж в §7. Дата: 2026-07-29.

## 1. Контекст и источник

Пользователь указал на [scrn.gallery](https://scrn.gallery), конкретно на `https://scrn.gallery/app/wb-bank?tab=flows` — «нравится, как нарезаны сценарии и полнота». Изучено по живым страницам (Playwright) **и** по их Nuxt-payload, поэтому известна не только картинка, но и модель данных.

**Что там устроено:**

- Каталог — четыре среза одной базы экранов: «Приложения», «Паттерны», «UI Элементы», «Сценарии»; сценарий — самостоятельная сущность с кросс-продуктовой таксономией.
- Страница приложения: три вкладки-счётчика — «309 экранов», «82 сценария», «5 видео». Счётчик и есть заголовок вкладки: полнота декларируется числом.
- Вкладка «Сценарии»: слева дерево, справа вертикальная простыня секций «Название / N экранов», каждая — горизонтальная лента экранов; действия секции — ♥, «скопировать ссылку», «скачать».
- **Дерево — ядро находки.** `flow.parent` даёт вложенность до 4+ уровней (`Главный экран → Переводы и платежи → Перевод по номеру телефона → Квитанция о переводе`). Главная линия остаётся короткой (2–18 экранов), полнота уезжает в детей.
- Лайтбокс: breadcrumb, крупная лента, при ховере — **зоны-хотспоты с подписью цели** («Текущий сценарий» либо имя другого сценария).
- Модель: `screen { zones:[{x,y,w,h в %, screen_id, flow_id}] }`, `flow { name, parent, screens[], tags }`. Экраны **переиспользуются** между сценариями: сценарий — упорядоченная выборка, а не копия. Плюс `status {new|updated, until}`.

**Где мы сейчас.** `flowSchema` (`src/prototype/schema.ts:92`) плоский; лимиты `FLOWS_LIMIT=12`, `FLOW_STEPS_LIMIT=50`, `FLOW_TOTAL_STEPS_LIMIT=200`. В плеере — `<select>` (`ScenarioBar.tsx:134`) и guided browse через `?flow=&step=`. Вид `/p/:id/cjm` рисует **живые** тайлы дорожками по флоу с рёбрами и легендой верификации. То есть у нас есть то, чего нет у scrn.gallery (живой рантайм, реальные хотспоты, verified-рёбра), и нет трёх их вещей: иерархии, читаемой ленты по каждому сценарию и подписей на зонах.

**Что именно даёт простыня поверх существующих дорожек** (важное уточнение после ревью): в дорожках якорные шаги ветки не имеют собственного тайла — `collectSegments` их пропускает (`lanesLayout.ts:184-195`), поэтому **прочитать ветку end-to-end сегодня невозможно**, видно только её отклонение от главной линии. Лента даёт полную последовательность каждого флоу. Это и есть «нарезка сценариев»; рёбра и легенду верификации простыня не дублирует — они остаются в дорожках.

**Терминологическая коллизия.** «Сценарий» в кодовой базе занято дважды: `doc.flows` (строки `player.scenarioSelect`, `cjm.flowsCount`) и `prototype_scenarios` — записанные рекордером прогоны (`src/prototype/scenario.ts`, `scenarioPanel.tsx`, миграция v19). Решение v2: в UI флоу остаются **«Сценарии»**, записи рекордера переименовываются в **«Проверки»** (они и есть assertions — `expectScreen`/`expectText`/`expectDisabled`). Схема, API и имена таблиц не меняются; в коде — `flow*` против `recordedScenario*`.

## 2. Ключевое решение: дочерние флоу — не дорожки

Это главный вывод ревью и центральный контракт плана.

`refinePrototypeDoc` применяет правило **«adjacent main-flow anchors must be consecutive in the forward direction»** ко **всем** флоу (`schema.ts:188-199`), а не только к веткам первого уровня. Правило существует затем, чтобы геометрия дорожек (`lanesLayout.ts:115-117`, «главный флоу + заякоренные ветки») была выразима. Именно детальные вложенные флоу ради которых вводится `parentId` («Квитанция о переводе», касающаяся двух неподряд идущих экранов главной линии) это правило нарушают → `422` на save. Поднятие лимита ничего не чинит.

**Контракт v2:** флоу с `parentId` — **не дорожка**.

- `refinePrototypeDoc`: правило anchor-adjacency применяется только к флоу **без** `parentId`. Дочерние флоу от него освобождены.
- `validate.ts:527` (warning «note on a main-flow anchor is not displayed») — тоже только для корневых веток: у дочерних флоу свои тайлы, и заметка отображается.
- `computeCjmLanes` строит дорожки **только по корневым флоу** (`parentId === undefined`). Для существующих документов (ни одного `parentId`) поведение побитово прежнее.
- Дочерние флоу видны в режиме «Сценарии», в дереве плеера и в guided browse — везде, где порядок задаётся деревом, а не геометрией дорожек.

## 3. Цели / не-цели

**Цели v1.**

1. `flow.parentId` + валидация + освобождение дочерних флоу от anchor-алгебры (§2).
2. Обратный индекс «экран → в каких сценариях участвует» — работает уже на **сегодняшних плоских** флоу.
3. Режим «Сценарии» в `/p/:id/cjm`: простыня секций с лентами живых тайлов + дерево слева; ленивое монтирование, распространённое **и на существующие дорожки**.
4. Дерево вместо `<select>` в плеере + breadcrumb.
5. Оверлей зон с подписью цели в плеере.
6. Терминологический разъезд «Сценарии» / «Проверки».
7. Авторская поддержка иерархии: рецепт в формате + скиллы + один реально переавторенный прототип.

**Не-цели v1 (осознанно, с обоснованием).**

- **`flow.tags`** — UI-среза по тегам в v1 нет, значит поле навсегда входит в strict-схему, JSON Schema, закоммиченный OpenAPI и `revisionDiff` без единого потребителя. Вводить вместе с потребителем. Теги уровня прототипа уже есть (миграция v16) — база для будущего среза не пустая.
- **Правила readiness** (`flow/screen-uncovered`, `flow/no-description`). В `server/readiness.ts:30-41` список гейтов закрыт, статусы — `pass|warn|fail|unknown`, уровня `info` не существует; новый gate-id тянет `server/contracts.ts` + регенерацию OpenAPI + `contract.test.ts`. А warning из `validatePrototype` попадёт в гейт `schema` и перекрасит его `pass→warn` у большинства прод-прототипов (экран вне флоу — норма), и при `EASYUI_PUBLISH_GATES=schema:warn` начнёт блокировать публикацию. Метрику покрытия считаем в UI из `CjmLayout.unassigned` — ноль серверной работы.
- **`flowLink.ts` и `ShareDialog`.** `ShareDialog` — про серверные токенизированные гранты (`createPrototypeShare`), а `exchangeShareToken` (`server/routes/share.ts:39-51`) пробрасывает в 303 `Location` **только** `mobile`, теряя `flow`/`step`. Deep-link на сценарий внутри share-гранта — самостоятельная серверная задача. В v1 «Скопировать ссылку» — обычная кнопка внутреннего URL в дереве/секции.
- Кросс-прототипный раздел «Сценарии», видео, ♥/коллекции, статусы `new/updated`, переезд флоу из документа в таблицу, автогенерация дерева из рекордера.

## 4. Задачи

Три задачи, **строго последовательно** — это снимает все конфликты владения, найденные ревью (`src/app/strings/player.ts` хотели три задачи сразу, `CjmView.tsx` — тоже три, причём в неверном порядке).

### T1 — Схема, обратный индекс, авторская поддержка

Владение: `src/prototype/schema.ts`, `src/prototype/validate.ts`, новый `src/prototype/flowGraph.ts` (+ тесты), `src/cjm/lanesLayout.ts` (фильтр корневых флоу), `src/editor/docDiff.ts`, `server/contracts.ts`, `server/openapi.json` (регенерация), `server/contract.test.ts`, `server/routes/meta.ts`, `docs/prototype-format.md`, `docs/server-api.md`, `test/fixtures/`, `e2e/starter-ds.fixture.ts`, `.claude/skills/author/SKILL.md`, `.claude/skills/yp-prototype/SKILL.md`.

**Схема** (аддитивно, `version` документа остаётся `1`; `tags` не вводим):

```ts
parentId: slugSchema.optional(),
```

Правила (в `refinePrototypeDoc`; локальный generic на строке `schema.ts:147-151` типизирует флоу как `{id, steps}[]` — расширить, иначе не затайпчекается):

- `parentId` ссылается на существующий флоу документа;
- **родитель обязан идти раньше ребёнка в массиве** — это нормативное правило, оно же даёт ацикличность (строго прямое ребро не может замкнуться) и вычисление глубины в один проход. Отдельных проверок на цикл и самоссылку не добавляем: они были бы избыточны и давали бы по три перекрывающихся issue на одно нарушение;
- глубина ≤ `FLOW_DEPTH_LIMIT = 4`;
- `flows[0]` обязан быть корневым;
- anchor-adjacency и warning про note на якоре — только для флоу без `parentId` (§2).

**Лимиты в T1 не меняются.** `FLOWS_LIMIT` остаётся 12, `FLOW_TOTAL_STEPS_LIMIT` — 200. Подъём вынесен в T4 и гейтится измеренным перф-бюджетом (§5).

**`src/prototype/flowGraph.ts`** — чистый модуль, единственный источник производных структур:
- `buildFlowTree(flows)` → узлы с `depth`, `children`, `path` предков. Порядок обхода — **явный DFS** по порядку массива: правило «родитель раньше ребёнка» не пиннит порядок поддеревьев (чередование законно), а T2 опирается на «порядок секций = порядок дерева»;
- `flowBreadcrumb(flows, id)`;
- **`screenFlowIndex(doc)`** → `Map<screenId, {flowId, stepIndex}[]>` — обратный индекс переиспользования. Работает на плоских флоу и даёт ценность в день выката, независимо от того, набьёт ли кто-нибудь иерархию.

**Вакуумность для сохранённых ревизий (критично).** `storedPrototypeDocSchema` гоняет тот же `refinePrototypeDoc` (`schema.ts:214-217`), а `parseStoredPrototypeDoc` превращает отказ в `422 invalid_stored_revision` **на чтении** (`server/repos/prototypes.ts:43-46`) — прототип станет неоткрываемым в проде. Обязательный тест: все `test/fixtures/*.json` проходят `storedPrototypeDocSchema`; каждое новое правило вакуумно при отсутствии `parentId`. Перед деплоем — dry-parse на копии прод-данных.

**Контракты.** `limits`/`features` в `server/contracts.ts:1364-1376` — явные списки полей; `server/contract.test.ts` сравнивает их целиком через `toEqual`; `verify:openapi` байт-сравнивает закоммиченный `server/openapi.json`; `docs/server-api.md:736` хардкодит литеральные значения лимитов. Добавляем `limits.flowDepth` и `features.flowTree` — и правим все четыре места, иначе `npm run verify` красный.

**Авторская поддержка** (иначе `parentId` — мёртвое поле: UI редактирования флоу не существует, `grep flows src/editor/*.tsx` пуст, скиллы про флоу молчат): рецепт дерева в `docs/prototype-format.md`, упоминание в скиллах `author` и `yp-prototype`, фикстура `test/fixtures/flows-tree.json` (3 уровня) + засев в `ensureStarterPrototypeSuite` (`e2e/starter-ds.fixture.ts:141`). `docDiff.ts:89-106` учит показывать изменение `parentId`.

Done: `npm run verify` зелёный (включая `verify:openapi` и `contract.test.ts`); unit-тесты на каждое правило и на вакуумность; тест `computeCjmLanes` — дорожки строятся только по корневым; unit-тесты `flowGraph` (DFS-порядок, breadcrumb, обратный индекс на плоских и на вложенных флоу); `/api/capabilities` отдаёт новые поля.

### T4 — Подъём лимитов (гейтится перф-бюджетом)

Владение: `src/prototype/schema.ts` (константы), `server/routes/meta.ts`, `server/contract.test.ts`, `docs/server-api.md`, `test/fixtures/flows-perf.json`.

Выполняется **только после** зелёного перф-бюджета из T2. `FLOWS_LIMIT` 12 → **24**, `FLOW_TOTAL_STEPS_LIMIT` 200 → **320**. Не 48/600: ревью показало, что при 48 флоу ширина грида дорожек (`columns = main.steps + Σ gapWidths`, `lanesLayout.ts:230`) уходит к ~550 колонкам × 584 px ≈ 320 000 px, и `CjmEdgesOverlay` даёт O(N) `getBoundingClientRect` на каждый из N колбэков.

Бюджет тела считаем честно: связывающее ограничение — **не шаги** (600 шагов ≈ 12 KB против `MAX_JSON_BODY_BYTES = 1 MiB`, `server/http.ts:39`), а экраны: реальный экран стоит 1.3–4.7 KB (`checkout.json` 1321 B/экран, `scale-demo.json` 4692), 318 B/экран в `flows-perf.json` — синтетика. Тест бюджета собирается из **реалистичного** экрана. `SCREENS_LIMIT` в коде нет вообще — лимит тела и есть де-факто лимит экранов; вводить ли явный лимит с внятной ошибкой вместо голого `413 payload_too_large` — решение внутри T4.

T1 → T2 → T3 → T4, последовательно. Параллелить нечего: три из четырёх задач иначе делят `CjmView.tsx` и `strings/player.ts`, а T4 по определению гейтится результатом T2.

Оркестратор независимо проверяет done-критерии и коммитит по зонам. Финальная приёмка: `npm run verify` + `npm run e2e` + runtime-прогон по `.claude/skills/verify/SKILL.md`.

**Перф обязан быть измерен до push в `main`:** по `.claude/skills/deploy/SKILL.md` откат первоклассный только через новый образ по SHA или revert+push, а регрессия CJM — чисто клиентская и поедет в SPA-бандле.

**Acceptance всей волны:** один реальный прод-прототип переавторен с трёхуровневым деревом флоу. Без этого `parentId` нечем подтвердить как продуктовую фичу.
