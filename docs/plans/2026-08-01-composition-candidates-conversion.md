# План: перевод используемых кандидатов в композиции

Дата: 2026-08-01
Версия: v1 (адверсариальное ревью не проводилось)
Вход: `docs/audit/2026-07-31-catalog-dedup-stage-a.md` (стадия A), спека
`docs/superpowers/specs/2026-07-30-composition-v2-dedup-migration-design.md` §5–§9
Предшественник: `docs/plans/2026-07-31-composition-v2.md` (проект 3 выполнен и в проде)

## 0. Резюме и главный тезис

Аудит пометил `composition-candidate` 295 артефактов, из них **47 версий / 42 уникальных id**
используются головными ревизиями прототипов. Классификация аудита механическая: «TSX уровня
molecule+ без заявленного `ownership.reason`». Она отвечает на вопрос «кто **не объяснил**, почему
он код», а не «кто **обязан** стать композицией».

Чтение исходников всех 42 показывает: **большинство — владельцы геометрии и поведения**
(скролл-вьюпорты со snap и масками, fixed/sticky-футеры, safe-area, анимации, трансформы,
скелетоны загрузки). Композиция — декларативное дерево опубликованных компонентов; она **не умеет
владеть CSS**. Значит для этой части правильный результат — не конверсия, а честный
`ownership.reason`, который снимает их из кандидатов навсегда.

Поэтому план — это **триаж с двумя разными исходами**, а не 42 одинаковые конверсии:

| Исход | Оценка по сигналам | Стоимость |
|---|---|---|
| **A. Оставить кодом**, дописать `ownership.reason` | ~26–28 | дёшево, нулевой визуальный риск |
| **B. Конвертировать** в параметризованную композицию | ~10–14 | дорого: авторинг + cutover + визуальная приёмка |
| **C. Собрать из существующих атомов** (тонкие обёртки) | ~2–4 | средне |
| **D. Сначала извлечь атом**, потом B/C | по факту триажа | дорого, откладывается |

Обещание плана: **ноль кандидатов без решения**, а не «42 композиции».

## 1. Установленные факты

### 1.1 Данные прода (снапшот 2026-07-31, `catalogRevision dbb54a9d…`)

- 42 уникальных id, 47 версионных строк: часть id закреплена головами на **разных версиях**
  (например `yp-payment-method-card` v17 и более ранние) — цель миграции адресуется парой
  `(id, version)`, а `typeMap` адаптера — по **имени** компонента.
- Затронуто **10 голов прототипов**, они группируются в семейства:

| Семейство | Головы | Кандидатов |
|---|---|---|
| App Home | `pay-app-home-v1`, `pay-app-home-pay-club`, `magnit-loyalty-entry-flow`, `acceptance-magnit-tree` | 16 (`yp-app-home-*`, `yp-promo-banner`, `yp-paybox-nav-bar`…) |
| CPQR | `cpqr-scenario`, `post-payment-loyalty-recovery` | 14 (`yp-cpqr-*`, `yp-banner-mini`) |
| CTYP / paybox | `ctyp-paybox-scenario`, `ctyp-single-offer` | 11 (`yp-payment-*`, `yp-full-payment-block`, `yp-success-payment-card`) |
| Magnit loyalty | `magnit-loyalty-july`, `post-payment-loyalty-recovery` | 13 (`yp-magnit-*`) |
| Pay Club | `pay-club-combo-demo` | 6 |

  Один компонент почти всегда сидит в нескольких головах, поэтому **батч = компонент, а не экран**:
  cutover переписывает все затронутые головы одной транзакцией.
- В проде уже есть **41 атом** (`yp-box`, `yp-text`, `yp-icon`, `yp-spacer`, `yp-separator`,
  `yp-badge`, `yp-button`, `yp-amount`, `yp-link`, `yp-shimmer`, `yp-skeleton` …) — материал для
  сборки композиций существует, отдельная волна «сначала напишем атомы» в общем случае не нужна.
- 14 из 42 несут именованные слоты, то есть уже работают как контейнеры.

### 1.2 Ограничения платформы, определяющие таксономию

1. **Композиция не владеет стилями.** Её элементы — только host-примитивы и опубликованные
   компоненты своей дизайн-системы. Скролл, маски, snap, `position: fixed/sticky`, safe-area,
   анимации, `transform`, скелетон-анатомия выражаются **только кодом**.
2. **`repeat` привязан к state, а не к параметру**: `repeat.statePath` — абсолютный указатель в
   `doc.state` **хоста**. Композиция не принимает массив параметром и не итерирует его. Значит
   populated-блоки конвертируются **фиксированной арностью** (`firstTitle/secondTitle/thirdTitle`
   → три элемента с параметрами) либо требуют state-контракта у хоста — второе делает композицию
   несамодостаточной и по умолчанию запрещено этим планом.
3. **Глубина вложенности 5**, бюджеты раскрытого экрана 500 элементов / глубина 50.
4. **`@eui/Composition` не принимает `repeat`**, не несёт `region` (регион маркирует экран).
5. **Гейт переиспользования в `enforce`**: любой новый компонент требует `intent`, дубликат даёт
   терминальный `409` без ретраев. Новые атомы — только через поиск кандидата.
6. **Атомарная политика**: новый TSX уровня molecule+ без `ownership.reason` не публикуется
   (`422 atomic_policy_violation`). Та же метадата — инструмент исхода A.
7. **Неизменяемые версии** продолжают пиновать старые бандлы; мягкое удаление артефакта возможно
   только после нуля использований в головах, физическое — отдельной GC-операцией.

### 1.3 Механизм замены

Замена компонента композицией уже реализована и проверена: `compositionConversions` в плане
миграции + `POST /api/catalog/migrations/{prepare,:runId/apply,:runId/rollback}`. Cutover берёт
maintenance-lock, снимает удерживаемый на диске бэкап и переписывает головы одной транзакцией;
откат восстанавливает состояние даже после рестарта процесса.

## 2. Таксономия решений

Решение по каждому кандидату принимается по исходнику, а не по метаданным.

**A — оставить кодом.** Компонент владеет хотя бы одним: прокручиваемым вьюпортом, маской или
snap; `position: fixed/sticky`; safe-area; анимацией/переходом/трансформом; состоянием (`useState`/
`useEffect`/`useRef`); измерением DOM; скелетон-анатомией загрузки. Действие: новая версия с
`ownership.reason` (и `scope`, если очевиден). Головы не трогаются, визуальный риск нулевой.

**B — конвертировать.** Компонент — контент-блок фиксированной арности: набор строк, сумм, иконок и
картинок, разложенный существующими атомами; вся вариативность уже выражена пропсами. Действие:
композиция v2 с параметрами 1:1 к пропсам, конверсия через адаптер, cutover, визуальная приёмка.

**C — собрать из атомов.** Тонкая обёртка (карточка, строка, лист) без собственной геометрии, чья
разметка целиком покрывается `yp-box`/`yp-text`/`yp-icon`/`yp-separator`. Отличается от B только
объёмом: параметров мало, слотов может не быть.

**D — сначала атом.** Внутри есть повторяющийся кусок, которого нет в каталоге атомом. Действие:
завести атом (с `intent`, через гейт), затем B/C. Если атом окажется дубликатом — терминальный STOP
и возврат в триаж.

Спорный случай — **только `overflow: hidden` ради скругления**: это не владение геометрией, такой
компонент идёт в B/C (`yp-box` умеет радиус и клип).

## 4. Процедура одной конверсии (B/C)

1. **Снять эталон.** `driver.mjs baseline <protoId>` для каждой затронутой головы — до любых
   изменений. Без эталона конверсия не начинается.
2. **Автор композиции.** Документ v2: `atomicLevel`, `scope`, параметры 1:1 к пропсам компонента
   (имена и типы сохраняются — это делает адаптер тривиальным), слоты 1:1 к слотам компонента.
   `driver.mjs composition <id> <doc.json> --design-system yandex-pay` → `composition publish`.
3. **Собрать план миграции**: `compositionConversions[{from:{kind:"component",id,designSystem},
   toCompositionId, adapter}]`, `catalogRevision`/`dataFingerprint` — из свежего
   `GET /api/catalog/migrations/audit`. Адаптер: `typeMap` со старого имени на `@eui/Composition`,
   `props` — переносы/дефолты/enum-мэппинги, `slots` — маршрутизация детей. Отбрасывание
   заполненного пропса, обработчика или слота **запрещено** без документированного исключения.
4. **`prepare`** — фиксирует прогон и staging; устаревшие отпечатки дают `409` до записей.
5. **Проверить кандидатов на клоне.** Прогнать раскрытие и рендер изменённых экранов на копии
   данных, сверить с эталоном: ожидание — `diffPercent = 0`.
6. **`apply`** — cutover под maintenance-lock с бэкапом.
7. **Приёмка**: `driver.mjs check <protoId>` по каждой голове (диффы), `readiness`, render-status,
   `usages` старого компонента = 0 в головах.
8. **Мягкое удаление** старого компонента (реестр замен уже содержит запись). Физическое удаление —
   не здесь.
9. **Провал любого шага 5–7** → `rollback` прогона, компонент остаётся, кандидат возвращается в
   триаж с записью причины.

## 5. Волны

| Волна | Содержание | Критерий приёмки |
|---|---|---|
| **W0. Триаж и эталоны** | Решение A/B/C/D по всем 42 с одной строкой обоснования на артефакт; эталоны по 10 головам | таблица решений в `docs/audit/2026-08-01-candidate-triage.md`; ноль артефактов без решения; baseline-set у каждой из 10 голов |
| **W1. Метадата (исход A)** | Публикация новых версий с `ownership.reason`/`scope` для всех A | `GET /api/catalog/migrations/audit` больше не числит их `composition-candidate`; головы не изменились; ноль визуальных диффов (бандл не менялся по рендеру — только метадата) |
| **W2. Пилот** | Одна конверсия целиком по §4, обязательно с учебным `rollback` и повторным `apply` | зелёная приёмка §4.7; отработанный откат; журнал пилота в плане |
| **W3. Семейство Magnit** | B/C-кандидаты `yp-magnit-*` (до 8) | по §4 на каждый; `diffPercent 0` на `magnit-loyalty-july`, `post-payment-loyalty-recovery`, `magnit-loyalty-entry-flow` |
| **W4. Семейство CPQR** | `yp-cpqr-action-footer`, `yp-cpqr-status-bar`, `yp-cpqr-tab-bar`, `yp-banner-mini` (по итогам W0) | `diffPercent 0` на `cpqr-scenario` |
| **W5. App Home / Pay Club** | `yp-app-home-payment-button`, `yp-pay-club-partner-card`, `yp-base-card-oneline` и то, что W0 отнесёт к B/C | `diffPercent 0` на четырёх головах App Home и `pay-club-combo-demo` |
| **W6. Отчёт** | Итоговый артефакт §12 спеки: было/стало по видам и уровням, все замены, переписанные головы, исключения, ссылки на эталоны и бэкапы | отчёт в `docs/audit/`, память проекта обновлена |

Волны W3–W5 независимы по данным (разные семейства компонентов), но **последовательны по
cutover**: каждый `apply` меняет `dataFingerprint`, поэтому подготовленный ранее план протухает.
Готовить план следующей партии — только после завершения предыдущей.

## 6. Визуальная приёмка

- Для замены «тип в тип» ожидание строгое: **`diffPercent = 0`** против эталона, снятого до
  конверсии. Любое ненулевое значение — это либо ошибка адаптера, либо намеренная правка, которую
  надо внести в план как исключение с before/after.
- Ошибки продукта, отсутствующие снимки, ошибки захвата и **неожиданно изменившиеся экраны** —
  блокируют cutover, а не «объясняются в отчёте».
- Глобального порога «допустимого» процента не существует.

## 7. Риски и терминальные STOP

1. **`overflow` как ложный сигнал в обе стороны.** Триаж по маркерам — эвристика; решение
   принимается чтением. STOP: если в W2–W5 конверсия даёт ненулевой дифф из-за клипа/скролла —
   артефакт немедленно переводится в A, а не «докручивается» стилями через атомы.
2. **Гейт переиспользования (`enforce`).** Новый атом в исходе D может получить `409
   component_reuse_required` — это терминально: берём предложенный канон либо возвращаем артефакт в
   триаж. Обход `--force-new` — только решением человека.
3. **State-контракт вместо параметров.** Соблазн выразить рельс через `repeat` по state хоста
   делает композицию несамодостаточной и ломает переносимость между прототипами. Запрещено планом;
   исключение — только с явным решением и записью в отчёт.
4. **Пины на разных версиях.** Один id, закреплённый головами на разных версиях, требует всех
   координат `(id, version)` в плане; пропуск версии оставит голову на старом типе и провалит
   критерий «ноль использований».
5. **Протухание плана между `prepare` и `apply`.** Любая публикация в каталоге меняет отпечаток.
   Организационное правило волн: во время cutover-окна другие агенты в прод не публикуют.
6. **Регресс доступности.** Populated-блоки несут `accessibleLabel`/`aria` — при переносе в
   композицию их обязан принимать соответствующий атом; потеря метки = провал приёмки.

## 8. Инструментальный пробел

`driver.mjs` не умеет работать с миграцией каталога — все пять эндпоинтов сегодня доступны только
через `curl`. Для волн W2–W5 это ручной шаг с риском опечатки в плане (JSON с адаптером).
Задача W2-0: добавить `driver.mjs migration audit|prepare|apply|rollback [--plan file.json]` с
`--json`, чтобы cutover шёл одним верифицируемым вызовом и попадал в логи так же, как остальной
авторинг.

## 9. Оценка

- W0 — один проход по 42 исходникам; самая ценная волна, дешёвая.
- W1 — механическая, но это 26+ публикаций; каждая проходит publish-typecheck и гейт ролей.
- W2 — пилот с откатом; закладывать больше времени, чем на любую последующую конверсию.
- W3–W5 — по §4 на каждый артефакт; реалистично 2–4 конверсии на волну, а не «все сразу».

## 10. Вне объёма

- **248 кандидатов без использования в головах**: конверсия бессмысленна, для них дешевле
  архивация; отдельное решение после W6.
- Физическое удаление отставленных бандлов (GC при нуле и неизменяемых использований).
- Композиции для новых экранов «с нуля» — это авторинг, а не миграция.
