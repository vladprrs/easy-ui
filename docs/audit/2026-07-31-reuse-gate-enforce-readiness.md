# Готовность reuse-gate к режиму enforce

Дата решения: 2026-07-31
Статус: **ОТМЕНЕНА 2026-07-31** решением владельца проекта —
[запись о включении enforce](2026-07-31-reuse-gate-enforce-decision.md).
Исторический вердикт ниже (**NOT READY / KEEP SHADOW**) сохранён как есть: он описывает
состояние критериев, а не запрет, который нельзя переопределить. Владелец воспользовался
предусмотренной в §«Повторная приёмка» веткой «принять риск и разрешить `enforce` на
доказательствах T0».

Это запись решения по критерию §5.4
[плана reuse-enforcement](../plans/2026-07-31-component-reuse-enforcement.md#5-порядок-деплоя),
а не обещание автоматически включить `enforce`. До новой подписанной записи приёмки
production должен оставаться в `REUSE_GATE=shadow`.

## Исходная точка окна

Первичное доказательство: в статусе Dokploy на дату записи latest deployment —
`2026-07-31T13:41:42.444Z done — fix(deploy): default reuse gate to shadow`.

При непрерывной работе этого deployment в `shadow` календарные 14 дней истекут не раньше
`2026-08-14T13:41:42.444Z`. Это только нижняя граница: фактический отсчёт должен начинаться не
раньше подтверждённого времени завершения deployment, а при любом разрыве непрерывности
`shadow` — с подтверждённого начала нового непрерывного окна.

## Проверка конъюнкции §5.4

| Критерий | Статус на 2026-07-31 | Доказательство / пробел |
|---|---|---|
| Отчёт T0 принят; `policyVersion >= 1`; доля пойманных известных дубликатов зафиксирована | **PASS** | [Калибровочный отчёт T0](2026-07-31-matcher-calibration.md) принят; итоговая политика — `policyVersion 1`, метрики воспроизводимы и зафиксированы. |
| Не менее 14 дней непрерывного production shadow | **FAIL** | Окно началось 2026-07-31; его календарная нижняя граница — `2026-08-14T13:41:42.444Z`, при условии подтверждённой непрерывности. |
| K = 20 последних первичных production create-решений в непрерывном shadow-окне | **NOT MEASURED / NOT SATISFIED** | В текущих API/CLI нет read-only seam для чтения production reuse-decisions; старые `enforce`-решения, записи вне окна и test/local БД не являются evidence. |
| Те же K = 20 решений принадлежат не менее чем двум разным акторам | **NOT MEASURED / NOT SATISFIED** | Нет read-only production-выборки для проверки акторов в фиксированном cohort. |
| В тех же K = 20 есть хотя бы одно `would_block` | **NOT MEASURED / NOT SATISFIED** | Нет read-only production-выборки; наличие события не выдумывается. |
| Каждое `would_block` в K = 20 разобрано и признано легитимным либо ложное срабатывание закрыто фикстурой | **NOT MEASURED / NOT SATISFIED** | Без фиксированного production cohort нельзя доказать ни полноту разбора, ни закрытие всех ложных срабатываний. |
| Для попыток из K = 20 отсутствуют supplemental-маркеры `intent_missing` | **NOT MEASURED / NOT SATISFIED** | В текущих API/CLI нет read-only seam для этой проверки; marker не считается отдельным первичным решением. |

Критерии безопасности образуют конъюнкцию. Один PASS по T0 не компенсирует FAIL или
неизмеренные пункты, поэтому включение `enforce` сейчас не допускается.

## Детерминированный cohort K = 20

При повторной приёмке сначала фиксируются cutoff `C` и подтверждённый непрерывный production
shadow-интервал `[S, C]`. Cohort строится только из строк с `gate_mode=shadow`,
`created_at` внутри `[S, C]` и первичным create-решением
`accepted_no_match|would_block|force_new`: сортировка `created_at DESC, id DESC`, затем ровно
20 последних строк. Старые строки `gate_mode=enforce` и любые строки вне `[S, C]` исключаются.
Если первичных строк меньше 20, K не набран.

Именно эти 20 строк должны одновременно дать не менее двух `actor_id`, хотя бы одно
`would_block` и разбор каждого `would_block` в cohort. Supplemental-строка
`decision=intent_missing` не считается 21-м первичным решением. Она связывается с попыткой из
cohort по совпадению audit identity tuple (`actor_id`, `artifact_kind`, `artifact_id`,
`design_system`, `source_or_doc_hash`, `catalog_revision`, `policy_version`, `gate_mode`) при
том же фиксированном cutoff и внутри того же `[S, C]`. Если из-за отсутствия request id
соответствие неоднозначно, критерий считается невыполненным; неоднозначность не используется
для исключения marker.

## Повторная приёмка после окна

Повторный review выполняется не раньше нижней границы окна и должен:

1. Подтвердить время завершения shadow-deployment и непрерывность
   `REUSE_GATE=shadow` на всём проверяемом интервале.
2. Зафиксировать cutoff `C`, получить через авторизованный read-only seam production-строки
   только из подтверждённого `[S, C]` и построить K = 20 по правилу выше. Если первичных
   строк меньше 20, перейти к human escalation.
3. На тех же 20 строках подтвердить не менее двух разных `actor_id` и хотя бы одно
   `would_block`.
4. Разобрать каждое `would_block` в K = 20: признать легитимным либо приложить фикстуру,
   закрывающую ложное срабатывание.
5. По audit identity tuple, тому же cutoff и тому же интервалу подтвердить отсутствие
   supplemental-маркеров `intent_missing` для всех 20 попыток; markers не добавлять к K.
6. Повторно сослаться на принятую T0-калибровку и фактически действующий `policyVersion`.
7. Выпустить новую запись с именем владельца проекта, временем решения, приложенными
   доказательствами и явной подписью решения.

Если первичных решений меньше 20, K не набран и автоматического перехода нет. Владелец
проекта должен явно выбрать одно из двух решений: продлить `shadow` до достаточной выборки
либо принять риск и разрешить `enforce` на доказательствах T0. Безымянная роль или прежняя
запись это решение не заменяет.

Любой будущий `REUSE_GATE=enforce` выполняется отдельным deployment только после такой новой
подписанной записи. Текущая запись запрещает менять Dokploy env, сама его не меняет и не
выполняет redeploy.
