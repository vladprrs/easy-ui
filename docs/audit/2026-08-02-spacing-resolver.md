# Аудит spacing-резолвера тем (план 2026-08-02, P6.3 / волна W4)

Дата: 2026-08-02. Инструмент: `scripts/audit-spacing-resolver.ts` (`~/.bun/bin/bun scripts/audit-spacing-resolver.ts --db <sqlite>` / `--json <design-systems.json>`).

## Зачем

Волна W4 чинит две дыры `space.*`:

- **(а) omission** — полный PATCH токенов, из которого `space.*` выпали целиком, молча уводил шкалу на базовую (для DS вне `systemScales` — на каноническую);
- **(б) base-drop** — частичные `space.*`-оверрайды мерджились на **каноническую** шкалу, а не на базовую шкалу DS (`spacingScale.ts:44` vs `:54`).

`resolveSpacingScale` стоит на read-пути (сводка DS, `/api/capabilities`, пины ревизий, съёмка), поэтому фикс версионирован: колонка `design_system_versions.spacing_resolver` (миграция v23), существующие версии — `1` (legacy, байт-в-байт), новые — `2`. Аудит отвечает на вопрос «где включение резолвера 2 задним числом сдвинуло бы геометрию», то есть проверяет безопасность самой модели, а не только фикса.

Колонки отчёта: `(ds, version, storedResolver, space.*, fallbackTriggered, baseDropped, differs)`.
`fallbackTriggered` — legacy-резолвер откатился на каноническую шкалу (невалидный/немонотонный набор); `baseDropped` — legacy потерял базу DS вне фолбэка; `differs` — итоговые шкалы резолверов 1 и 2 расходятся.

## Ограничение по прод-данным (честно)

Сырой прод-БД в репозитории нет. Доступны только логические выгрузки:

- `.backups/prod-v2-20260729/design-systems.json` — ответ `GET /api/design-systems`, то есть **только последняя** версия темы каждой системы (`yandex-pay` v7); исторические версии в снапшот не попадают;
- `.backups/prod-v2-20260729/full-export.zip` → `manifest.json` — тема одной **пиннутой** версии (`metaVersion 4`), тоже без истории.

Полная история версий тем прода аудитом не покрыта. Это приемлемо ровно потому, что фикс огорожен `spacingResolver`: **все существующие строки (прод в том числе) остаются на резолвере 1 и не меняют шкалу ни на байт** — прод-версии физически не могут получить `2` без нового PATCH. Проверку истории имеет смысл повторить одной командой на прод-копии перед следующей DS-миграцией:

```
~/.bun/bin/bun scripts/audit-spacing-resolver.ts --db <копия prod easy-ui.db>
```

## Наблюдения

1. **Расхождение резолверов сегодня структурно невозможно на живых данных.** Оно наблюдаемо только там, где базовая шкала DS не каноническая — сегодня это `wireframe` и `shadcn`. Обе системы — ретайрнутые builtin'ы, их темы неизменяемы (`405 method_not_allowed` на PATCH), поэтому версию с резолвером `2` они получить не могут. У `yandex-pay` и у любой кастомной DS база совпадает с канонической шкалой, и резолверы 1 и 2 дают одинаковый результат.
2. **Дыра (а) в проде реальна и массова.** В `.e2e-data/audit` (снимок прод-подобных данных `yandex-pay`) версии 2, 4, 6, 8 не содержат ни одного `space.*` — full-replacement-патчи периодически «теряли» всю шкалу, и она молча уезжала на базовую. Видимых последствий не было только потому, что база `yandex-pay` совпадает с канонической шкалой; на DS с другой базой это был бы тихий сдвиг геометрии. Наследование `space.*` из базовой версии (резолвер 2, поле ответа `inheritedSpaceTokens`) закрывает именно этот сценарий.
3. **Фолбэков (невалидные/немонотонные наборы) в данных нет** — write-path 422 (`spaceTokenIssues`) работает; единственный источник таких версий — прямые вставки в БД (grandfathering малформленных тем в тестах).

## Вывод

Включение резолвера 2 для **новых** версий безопасно: ни одна существующая версия ни в одной доступной базе не меняет резолвнутую шкалу, а для старых версий путь не меняется вовсе (они читаются с записанным `spacing_resolver = 1`). Kill-switch `EASYUI_THEME_RESOLVER_V2_DISABLED=1` возвращает запись новых версий на резолвер 1 и отключает наследование `space.*`; discovery отражает состояние в `/api/capabilities` → `features.themeSpacingResolverV2`.
