# Глоссарий канонических ролей (`canonicalFor`)

Машинная версия — `server/catalog/roles.json`; этот документ и JSON обязаны перечислять
**одни и те же слаги** (проверяется тестом `server/agent-policy.test.ts`).

Роль — это **продуктовая задача**, а не имя компонента: «промо-баннер», «футер оплаты»,
«разделитель». Компонент объявляет `definition.canonicalFor: ["<slug>"]`, когда он —
*канонический* выбор системы для этой задачи. Роль без канонического носителя — нормальное
состояние; компонент без ролей — тоже.

## 1. Правила

- Слаг: `^[a-z0-9]+(?:-[a-z0-9]+)*$` (валидируется при извлечении definition,
  `server/components/extract-subprocess.ts`); не более **12** ролей на компонент.
- **Внутри одной дизайн-системы у роли не может быть двух активных носителей.** Попытка забрать
  занятую роль даёт терминальный `409 canonical_role_conflict` — и на `POST /components`,
  и на `POST /components/:id/publish` (`server/catalog/gate.ts`). Обход — только админский
  `reuseOverride` после решения человека.
- Пересечение `canonicalFor` — **блокирующий сигнал матчера независимо от score**
  (`server/catalog/matcher.ts`): роль объявляется осознанно.
- Роль **не** зависит от дизайн-системы: один и тот же слаг может иметь по одному носителю в
  `yandex-pay` и в другой системе.

## 2. Стартовый набор

Набор **стартовый**: он выведен из уже задокументированных ролей примитивов
(`docs/design/yandex-pay.md` §3, скиллы `yandex-pay`/`yp-prototype`) и из пар «near-duplicate»
аудита 2026-07-20, где две записи каталога делят одну продуктовую задачу
(`docs/audit/2026-07-31-matcher-calibration.md`, замер 7).

| Слаг | Роль | Кандидат в носители (`yandex-pay`) |
|---|---|---|
| `screen-shell` | каркас экрана: навигация, заголовок, контент, футер | `yp-screen` |
| `layout-primitive` | строка/колонка с gap и паддингами по шкале spacing | `yp-box` |
| `section-panel` | голая структурная секция без декора | `yp-panel` |
| `typography` | текстовый примитив системы | `yp-text` |
| `separator` | разделитель между блоками | `yp-separator` |
| `money-amount` | денежная сумма в локализованном формате | `yp-amount` |
| `promo-banner` | промо-баннер с изображением и CTA | `yp-promo-banner` |
| `badge` | компактный маркер статуса/скидки | `yp-badge` |
| `tooltip` | всплывающая подсказка у элемента | `yp-tooltip` |
| `collapsible` | раскрывающийся блок | `yp-collapsible` |
| `payment-method-card` | плитка выбора способа оплаты | `yp-payment-method-card` |
| `payment-cta-footer` | закреплённый футер оплаты с CTA | `yp-sticky-payment-footer` |
| `payment-success-card` | карточка успешной оплаты | `yp-success-payment-card` |

**Колонка «кандидат» — это предложение, а не факт.** На 2026-07-31 `canonicalFor` пуст у **всех**
прод-записей каталога (замер плана §5 и отчёта T0); проставление ролей выполняется новыми
ревизиями компонентов в рамках бэкфилла проекта 3 (`scripts/backfill-component-scope.ts`), а не
правкой сохранённых `definition_meta`.

### Пары, ожидающие триажа

Роль **не назначена** намеренно — решение принимает владелец дизайн-системы
(`needsTriage` в `roles.json`):

- `yp-split-discount-info` ↔ `yp-discount-info-with-cashback` — одна роль «инфо о скидке/кэшбэке» или две;
- `yp-radio-button` ↔ `yp-pseudo-radio` — скилл `yandex-pay` §2 объявляет их разными сущностями;
- `yp-app-home-savers` ↔ `yp-app-home-loans` — аудит признал осознанным форком, матчер блокирует пару (0.7845);
- `yp-base-card-mini` ↔ `yp-best-profit-base-card-mini` — одна роль с параметром или два блока.

## 3. Как пополнять

1. Убедись, что задача не покрыта существующим слагом (таблица выше) и что это действительно
   продуктовая задача, а не имя компонента.
2. Добавь запись в `server/catalog/roles.json` (`slug`, `ru`, `en`, при наличии `candidate`,
   `evidence` — ссылка на аудит/план, откуда взята роль) **и** строку в таблицу §2. Тест
   `server/agent-policy.test.ts` падает, если списки разошлись или слаг не проходит regex.
3. В том же PR укажи, какой компонент становится носителем роли, и опубликуй его ревизию с
   `canonicalFor`. Роль без носителя допустима, но тогда так и напиши в описании PR.
4. Если роль уже занята другим компонентом — это не повод для второго носителя: либо
   переиспользуй занявший компонент (см. `docs/agent-authoring-policy.md`), либо роль переносится
   осознанно (снять `canonicalFor` со старого носителя новой ревизией, затем поставить новому).

Слаги переименовывать нельзя: `canonicalFor` уже опубликованных версий иммутабелен, а
переименование тихо разведёт две записи об одной роли. Устаревшая роль помечается в JSON полем
`"deprecated": true` с указанием заменяющего слага и остаётся в файле.

## 4. Известный пробел (TODO)

Сервер **не** сверяет `canonicalFor` со словарём: проверяются только формат слага и уникальность
роли внутри системы. Любой слаг, прошедший regex, будет принят, в том числе опечатка
(`promo-baner`), и такая роль займёт «свою» ячейку уникальности, не конфликтуя с настоящей.

Предупреждение на неизвестный слаг должно жить рядом с проверкой уникальности —
`assertPublishRoleAvailable` / `matchAndDecide` в `server/catalog/gate.ts`, в том же наборе
`warnings[]`, которым гейт уже отвечает в фазе `shadow`; источником словаря станет этот файл
(`server/catalog/roles.json`). На 2026-07-31 такой проверки нет, и настоящий документ намеренно
не описывает её как существующую. Задача относится к бэкфиллу метаданных (проект 3), потому что
до бэкфилла предупреждение не на чем срабатывать: ролей в каталоге нет.
